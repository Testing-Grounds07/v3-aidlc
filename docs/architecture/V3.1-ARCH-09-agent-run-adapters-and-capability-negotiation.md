# V3.1-ARCH-09: Agent Run Adapters and Capability Negotiation

**Status:** Proposed architecture baseline  
**Version:** 0.1  
**Date:** 2026-09-17  
**Depends on:** V3.1-ARCH-02, V3.1-ARCH-04, V3.1-ARCH-06, V3.1-ARCH-07, and V3.1-ARCH-08

## 1. Purpose

This specification defines how V3-AIDLC sends bounded work to different AI systems, agent harnesses, or tool runners without making the rest of the framework depend on one provider.

In plain terms, an adapter is a translator. V3 describes a job in one standard form. The adapter translates it for a particular runner and translates the outcome back into one standard result.

Before any work is sent, V3 must be able to answer:

- What does this job require?
- What can this runner actually do right now?
- Is it cleared for this context and these tools?
- Does current authorization permit dispatch?
- Can its outcome be traced to the exact instructions, context, lease, and runner profile?
- Can an interrupted attempt be retried safely?

Provider reputation, model names, and conversational claims are not substitutes for this check.

## 2. Boundary

The Project Lead owns planning, authorization, runner selection, leases, context assembly, evidence evaluation, recovery, and acceptance.

An adapter owns only provider-specific translation and invocation. It cannot expand scope, grant itself tools, weaken context restrictions, mark its own evidence accepted, or decide that a work package is complete.

Provider-specific request and response payloads stay behind the adapter boundary. Canonical state stores governed V3 contracts and references to retained provider records, not opaque provider objects.

## 3. Capability Profile

Every available adapter publishes a Capability Profile containing:

- immutable profile, adapter, and adapter-version identities;
- provider and model identities;
- current availability status;
- supported roles, capabilities, modalities, tools, and network hosts;
- maximum context and output sizes;
- concurrency limit and maximum sensitivity;
- structured-output and streaming support;
- external-side-effect support;
- and whether invocation is idempotent.

A profile is a point-in-time declaration, not a permanent promise. Its canonical digest is pinned into each dispatch. If its content changes, it becomes a different effective profile and the job must be negotiated again.

Unknown capabilities are treated as absent. V3 does not infer vision support, tool access, privacy clearance, or reliability from a model or provider name.

`degraded` and `unavailable` profiles are not eligible for new work in this baseline. A future policy may define narrowly permitted degraded operation, but it must remain explicit.

## 4. Agent Run Request

The Project Lead creates one provider-neutral Agent Run Request for one bounded attempt. It identifies:

- run, project, and work-package IDs;
- requested role and objective;
- exact Context Manifest ID and digest;
- context size and sensitivity;
- required capabilities, modalities, tools, and network hosts;
- structured-output and external-side-effect requirements;
- maximum output size;
- completion criteria;
- current authorization decision;
- attempt number;
- and an idempotency key.

The request contains requirements, not a preferred provider. Provider selection occurs only after the request is complete.

## 5. Capability negotiation

Negotiation compares every declared requirement with one exact Capability Profile.

A runner is rejected when any of the following is true:

- it is not currently available;
- the requested role is unsupported;
- a required capability, modality, tool, or network host is missing;
- the context or output exceeds a declared limit;
- context sensitivity exceeds runner clearance;
- required structured output or external effects are unsupported;
- a retry needs idempotent invocation but the runner lacks it;
- or authorization is blocked or still requires a user decision.

Every rejection records exact reasons. Negotiation never silently removes a requirement to make a runner fit.

## 6. Selection

When several runners satisfy the job, the baseline selector is deterministic and prefers the narrowest sufficient runner:

1. least excess sensitivity clearance;
2. least excess context capacity;
3. least excess output capacity;
4. stable adapter ID ordering.

This is a safety baseline, not a claim that capacity alone determines quality. Later policy may add verified quality, latency, cost, locality, or sustainability evidence. Such factors must remain explicit and cannot override required capability or authorization checks.

## 7. Dispatch Envelope

After negotiation and lease acquisition, V3 builds a Dispatch Envelope that pins:

- the complete Agent Run Request and its digest;
- chosen adapter, version, profile, and profile digest;
- Context Manifest ID and digest;
- lease ID;
- attempt and idempotency identities;
- and the complete dispatch digest.

The adapter receives this immutable envelope. A result from a different context, profile, lease-bound attempt, or modified request is not interchangeable with the selected run.

Capability negotiation does not replace authorization, and authorization does not replace a lease. All three must succeed before dispatch.

## 8. Adapter interface

Every provider integration implements two logical operations:

- `capability_profile()` returns the current governed profile;
- `invoke(dispatch)` accepts a valid Dispatch Envelope and returns provider-specific output for normalization.

Provider adapters may internally use an API, local model, subprocess, managed agent, or human-assisted tool. Those details do not change the V3 boundary.

An adapter must not accept a dispatch when its current capability profile no longer matches the pinned profile digest. It reports the mismatch so the Project Lead can renegotiate.

## 9. Normalized result

The adapter maps provider output into a Normalized Agent Run Result containing:

- exact run, project, work-package, adapter, profile, context, and dispatch identities;
- start and finish times;
- completed, failed, blocked, or cancelled status;
- plain-language summary;
- artifact, evidence, Finding, and satisfied-criterion IDs;
- external-effect observations;
- usage counts;
- and a reference to the retained provider result.

Opaque provider payloads are not copied into canonical state. This avoids accidental disclosure, provider lock-in, and unstable state schemas.

## 10. Completion is a claim, not acceptance

A runner may report `completed`, but the Project Lead still evaluates evidence and Gates under ARCH-06.

The normalized result cannot claim completion unless every requested completion criterion is listed and supporting evidence exists. Failed, blocked, or cancelled runs cannot claim satisfied criteria.

This prevents a fluent answer, successful API response, or zero exit code from being mistaken for verified delivery.

## 11. External effects

External effects are permitted only when both the request and Capability Profile explicitly support them.

Each reported effect includes a stable effect key, type, observed status, and observation reference. Status is `succeeded`, `absent`, or `unknown`.

An adapter reporting an unapproved effect creates a contract violation and Finding. Unknown external state enters the ARCH-08 verification path before retry.

## 12. Failure and cancellation

Adapters normalize provider failures instead of hiding them. A failure summary should identify whether the cause was provider availability, rate limiting, context size, tool denial, malformed output, timeout, cancellation, or another known category.

Cancellation is cooperative unless the provider proves stronger guarantees. The Project Lead revokes or releases the lease and treats late output according to ARCH-08. A late result cannot mutate current state merely because the provider eventually finished.

## 13. Retry and recovery

Every attempt has its own lease and Dispatch Envelope. A retry recompiles context, rechecks authorization, obtains a current Capability Profile, renegotiates, and creates a new dispatch.

The same logical work may retain a correlation identity, but attempt and dispatch identities remain distinct. External effects are verified before retry. A capability or provider change never bypasses the original completion criteria.

## 14. Context and disclosure

ARCH-07 controls what the runner receives. The adapter receives only the selected Context Manifest and approved references. It cannot request broader project history merely because the provider supports a larger context window.

Secrets remain secret references. Provider credentials and raw secret values do not enter Agent Run Requests, profiles, results, or canonical event payloads.

## 15. Evidence and findings

Artifacts and evidence returned by a runner remain candidates until validated. Failed normalization, profile mismatch, unauthorized effects, missing completion evidence, and repeated malformed output create durable Findings where material.

Verified recurring behavior may become Learning. For example, repeated inability of one adapter version to produce valid structured output may influence future selection, but it does not silently rewrite that adapter’s declared profile.

## 16. Liaison behavior

The liaison explains provider selection in layman’s terms. Useful explanations include:

- “This runner has the tools and privacy clearance this job needs.”
- “This runner was rejected because it cannot access the required test environment.”
- “The AI says it finished, but V3 still needs evidence before accepting the work.”
- “The previous attempt may have changed an outside system, so V3 is checking before trying again.”

The liaison should not expose internal provider payloads, credentials, or unnecessary capability metadata.

## 17. Portability

The provider-neutral contracts allow a project to use different runners across stages, modes, workstreams, and attempts. A fast prototype runner may be suitable for an Exploration Mode task while an independently controlled runner performs Production-Ready verification.

Portability does not mean every provider is interchangeable. It means differences are declared, checked, recorded, and handled without changing the project’s core lifecycle contracts.

## 18. Bootstrap implementation

The bootstrap implementation provides:

- executable Capability Profile and Agent Run validation;
- deterministic capability negotiation and least-privilege selection;
- cryptographically digested requests and dispatches;
- normalized result validation;
- completion-evidence enforcement;
- external-effect authorization checks;
- JSON Schemas for all four public contracts;
- and tests covering mismatch, authorization, retry, integrity, normalization, and side-effect behavior.

The bootstrap intentionally does not include a live provider integration. Provider-specific adapters should be added only after these boundary contracts are accepted.

## 19. Acceptance criteria

ARCH-09 is complete when:

1. every dispatch is based on an explicit accepted negotiation;
2. unknown or missing capabilities fail closed;
3. blocked and user-decision-required work cannot dispatch;
4. the dispatch pins the exact request, context, profile, lease, and attempt;
5. provider output normalizes into one stable result contract;
6. a completion claim requires criteria and evidence;
7. unauthorized external effects are rejected;
8. retry requires a fresh governed attempt;
9. schemas parse and executable tests pass;
10. and no live provider dependency is required to verify the architecture baseline.
