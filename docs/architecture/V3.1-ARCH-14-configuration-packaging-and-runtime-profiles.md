# V3.1-ARCH-14: Configuration, Packaging, and Runtime Profiles

**Status:** Proposed architecture baseline  
**Version:** 0.1  
**Date:** 2026-09-17  
**Depends on:** V3.1-ARCH-03, V3.1-ARCH-04, V3.1-ARCH-07, V3.1-ARCH-09, V3.1-ARCH-11, V3.1-ARCH-12, and V3.1-ARCH-13

## 1. Purpose

This specification defines how V3-AIDLC is configured, packaged, started, upgraded, and run in different environments.

In plain terms, the same framework should work for one person experimenting on a computer, a development team, a privately hosted service, or a production system. Those situations need different amounts of infrastructure, but they must still follow the same fundamental rules. ARCH-14 defines the standard runtime profiles and prevents environment-specific settings from quietly changing V3's meaning or safety boundaries.

## 2. Architecture-baseline boundary

ARCH-14 closes the V3.1 architecture baseline. ARCH-01 through ARCH-13 define the lifecycle, orchestration, state, governance, agent, security, evidence, scheduling, recovery, and operational contracts. ARCH-14 defines how those contracts are assembled into an executable runtime.

Closing the architecture baseline does not mean the finished product is deployed. It means implementation can proceed against a coherent, versioned, testable design without inventing foundational behavior package by package.

## 3. Runtime principles

1. **One framework, several operating sizes.** Profiles change deployment weight, not the meaning of V3's contracts.
2. **Explicit beats hidden.** Every effective setting has an identifiable source and stable assembled digest.
3. **State authority cannot drift.** `state.db` remains the logical authority; readable snapshots never become writable truth.
4. **Secrets are referenced, not stored.** Configuration names where a secret comes from without containing its value.
5. **Production fails closed.** Missing provenance, telemetry, recovery, or security components prevent production readiness.
6. **Packages identify their contents.** Version and digest information allow operators to prove what was installed.
7. **Upgrades are migrations.** Compatibility, backup, rollback, and verification occur before promotion.

## 4. Standard runtime profiles

| Profile | Intended use | Plain-language description |
|---|---|---|
| `local` | One trusted user, development, trials, and prototypes | Everything needed to learn and build on one computer, without pretending it is a production service. |
| `team` | Shared development and internal collaboration | Central state, shared workers, audit history, credentials, and monitoring for a trusted team. |
| `hosted` | Persistent private service | A continuously available deployment with managed state, backups, monitoring, and private access. |
| `production` | User-facing or business-critical service | The complete security, provenance, monitoring, recovery, scaling, and operational-readiness boundary. |

Profiles are defaults, not risk disguises. A local process handling production data or causing external effects inherits the stronger applicable controls. A production deployment cannot select the local profile merely to bypass required evidence.

## 5. Required components

V3 recognizes these logical components:

- liaison;
- Project Lead;
- scheduler;
- worker;
- authoritative state;
- artifact and evidence storage;
- credential broker;
- telemetry pipeline.

Local use may combine several components in one process and omit credential brokering or exported telemetry when no external credentials or service obligations exist. Team and hosted profiles normally include all components. Production requires all eight, though one component may have several replicas.

Logical separation does not require eight servers. It means each responsibility has a defined interface and cannot gain another component's authority accidentally.

## 6. Configuration layers and precedence

Configuration is assembled in this order, from weakest to strongest:

1. framework defaults;
2. selected runtime profile;
3. project configuration;
4. environment variables;
5. command-line overrides.

Later layers override earlier layers at the most specific matching key. Object keys match without case sensitivity so an environment variable such as `V3__SCHEDULER__MAXCONCURRENCY` updates `scheduler.maxConcurrency` rather than creating a second setting.

Every assembly records the participating sources and a deterministic digest of the effective configuration. The digest lets evidence, startup reports, and incidents identify the exact settings in effect.

## 7. Protected settings

Normal overrides cannot change:

- `state.authority` away from `state.db`;
- `state.snapshotAuthority` away from `false`;
- `security.allowRawSecrets` away from `false`;
- or an already-required provenance-verification boundary.

Changes to these rules require a new governed framework version, not an environment variable. Unknown or conflicting configuration fails validation instead of being silently guessed.

## 8. Environment-variable convention

Environment overrides begin with `V3__`. Double underscores separate object levels. Values are parsed as JSON scalars or structures when valid; otherwise they remain strings.

Examples:

- `V3__TELEMETRY__ENABLED=true`
- `V3__SCHEDULER__MAXCONCURRENCY=8`
- `V3__PROVIDER__APIKEY=broker://providers/main`

Deployments expose only an allowlisted set of override keys in production. Environment access does not create permission to weaken governance.

## 9. Secret references

Secret-bearing fields accept references such as:

- `env://VARIABLE_NAME` for an explicitly permitted local or platform variable;
- `file://mounted/path` for a protected mounted secret;
- `broker://scope/name` for a credential-broker identity.

They do not accept raw secret values. The runtime resolves a reference only at the point of authorized use and does not write the resolved value into canonical state, configuration snapshots, telemetry, errors, or evidence.

Production uses brokered, short-lived credentials where supported. File and environment references are deployment adapters, not permission grants.

## 10. Paths and storage

Runtime paths are anchored to declared roots for state, artifacts, evidence, temporary work, and configuration. Relative paths cannot escape their root through `..`, symbolic-link confusion, or absolute substitution.

Temporary run data is separated from durable project data. Cleanup may delete disposable work only after evidence, recovery, and incident-preservation requirements are satisfied.

Local defaults favor understandable directories. Hosted and production profiles bind logical stores to managed services without changing their contract identities.

## 11. Package forms

The implementation may be distributed as:

- a Python package for library and command-line use;
- a source archive for inspection and controlled builds;
- a container image for workers or hosted services;
- and deployment bundles such as Compose or an orchestrator-specific package.

All forms derive from the same versioned source and include or reference a Package Manifest. A deployment bundle may add infrastructure configuration but cannot redefine lifecycle or governance semantics.

## 12. Package Manifest

The Package Manifest identifies:

- package and framework versions;
- required language/runtime version;
- supported state-schema versions;
- supported runtime-profile kinds;
- and packaged artifact paths with SHA-256 digests.

Artifact paths must remain inside the package and be unique. Compatibility checks fail when the framework version differs, the state schema is unsupported, or no usable profile kind is shared. Signing and provenance follow ARCH-12.

## 13. Versioning and compatibility

Framework, contract, state-schema, configuration-schema, adapter, and package versions are related but distinct. Implementations use semantic versioning where practical:

- patch changes correct behavior without changing a contract;
- minor changes add backward-compatible capability;
- major changes may require operator action or migration.

Compatibility is declared, then verified. The presence of similar version strings is not sufficient. Unsupported combinations stop startup before state mutation.

## 14. Startup sequence

A runtime starts in this order:

1. identify the package and verify its manifest and provenance;
2. select one runtime profile;
3. assemble and validate configuration;
4. verify paths, identities, permissions, and credential references;
5. connect to authoritative state without taking competing ownership;
6. verify schema and migration compatibility;
7. connect artifacts, evidence, adapters, and telemetry;
8. recover unfinished leases and runs under ARCH-08;
9. run health and readiness checks;
10. emit a Startup Report and accept work only if permitted.

Startup is idempotent. Repeating it does not duplicate project entities, migrations, events, or external effects.

## 15. Startup Report

The Startup Report records runtime and profile IDs, configuration digest, time, individual check results, and overall status:

- `ready` — all required checks passed;
- `not_ready` — at least one required check failed;
- `inconclusive` — evidence is missing or a check could not finish.

Only ready instances accept normal production work. A local development profile may remain usable with clearly reported optional limitations, but it cannot report production readiness.

## 16. Health and readiness

Liveness answers whether a process is running. Readiness answers whether it can safely perform its assigned role. A worker may be alive but not ready because state, credentials, adapters, or conflict reservations are unavailable.

Health endpoints reveal the minimum information necessary. Public responses do not expose configuration, dependency versions, project identities, stack traces, or credential references.

## 17. Shutdown and restart

Graceful shutdown stops accepting new work, allows bounded in-flight work to finish or checkpoint, releases leases, flushes durable events and telemetry, and records termination. Forced termination relies on lease expiry, idempotency, and recovery planning when the runtime restarts.

The runtime never marks unknown external effects as safely retriable. Those runs return through reconciliation.

## 18. Upgrade and rollback

An upgrade verifies the new package, compatibility, capacity, backup state, migration plan, and rollback path before mutation. State changes follow ARCH-13's expand, backfill, verify, switch, and contract phases.

Rollback is allowed only while the active state and artifact formats remain compatible with the earlier runtime. Once contraction removes the old representation, rollback requires an explicit restoration or forward repair plan.

## 19. Extensions and adapters

Providers, tools, state drivers, artifact stores, credential brokers, and telemetry exporters connect through declared adapter interfaces and Capability Profiles. Installing an extension does not authorize it.

Extensions declare version compatibility, capabilities, requested resources, provenance, and configuration schema. Unknown extension settings, duplicate identities, and incompatible versions fail closed.

## 20. Profile-specific expectations

### Local

- single trusted operator;
- SQLite state and local artifact/evidence directories;
- low concurrency and explicit resource ceilings;
- deny-all network unless a run receives access;
- no production-readiness claim.

### Team

- authenticated team identities;
- centralized state and shared artifacts;
- credential brokering and audit history;
- bounded concurrent work and team recovery procedures.

### Hosted

- persistent private endpoint;
- managed database and storage;
- encrypted connections, backups, telemetry, and service health;
- documented operator and update path.

### Production

- complete component set and environment separation;
- verified package provenance and dependencies;
- SLOs, budgets, tested recovery, on-call ownership, and incident process;
- controlled rollout and rollback;
- readiness evidence under ARCH-13.

## 21. User interaction

The main conversational AI may connect through the liaison without asking the user to understand V3 configuration. The liaison identifies the managed project and runtime, translates the user's goal, and explains profile or readiness limitations in ordinary language.

For example, it should say “this setup is safe for testing on your computer but has not been prepared for public users,” rather than merely reporting `PROFILE-LOCAL-01 / NOT_PROD_CAPABLE`.

The user may request technical details, but internal vocabulary is not the default interface.

## 22. Bootstrap implementation

The bootstrap supplies:

- `runtime-profile`, `runtime-assembly`, `package-manifest`, and `startup-report` schemas;
- standard local, team, hosted, and production profile examples;
- deterministic configuration assembly and secret-reference validation;
- Package Manifest and compatibility evaluators;
- and six runtime conformance scenarios.

The bootstrap does not yet provide a production server, containers, managed database implementation, credential broker, telemetry collector, deployment charts, installer, or upgrade command. Those are implementation-milestone deliverables built against this baseline.

## 23. Acceptance criteria

ARCH-14 is satisfied when:

1. four standard runtime profiles have clear and non-overlapping intent;
2. configuration precedence is deterministic and produces a stable digest;
3. protected state and security settings cannot be weakened by normal overrides;
4. raw secret values are rejected in favor of references;
5. production profiles require the complete component, provenance, telemetry, and recovery boundary;
6. package contents and compatibility are machine-checkable;
7. startup, readiness, shutdown, upgrade, and rollback behavior are explicit;
8. local and lightweight use cannot be confused with production readiness;
9. user-facing explanations remain understandable without framework vocabulary;
10. and the full ARCH-01 through ARCH-14 baseline passes automated verification and is recoverably checkpointed.
