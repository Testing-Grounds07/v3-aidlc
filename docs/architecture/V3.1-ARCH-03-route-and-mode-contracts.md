# V3.1-ARCH-03: Route and Mode Contract Schemas

**Status:** Proposed architecture baseline  
**Version:** 0.1  
**Date:** 2026-09-16  
**Depends on:** V3.1-ARCH-01, V3.1-ARCH-02  

## 1. Purpose

This specification turns Routes and Modes into governed, machine-readable contracts.

A Route defines the expected journey for an Intent or Workstream. It identifies Stages, allowed transitions, required and conditional Modes, Gate expectations, and controls that cannot be bypassed. A Mode defines how one kind of work is performed: its inputs, roles, permissions, outputs, evidence, completion criteria, budgets, and possible outcomes.

The Project Lead may tailor a Route, but it must do so through explicit, validated changes. It cannot silently omit a mandatory Mode, Gate, or risk control.

## 2. Separation of responsibilities

| Contract | Governs |
|---|---|
| Route Definition | Which Stages and Modes form an expected development path |
| Route Instance | How a Route Definition is tailored to a particular Intent or Workstream |
| Stage Definition | A lifecycle position and its allowed neighboring transitions |
| Mode Contract | How a reusable kind of work is executed and judged |
| Posture Profile | How evidence depth, review breadth, budgets, and checkpoint frequency vary |
| Risk Profile | Which controls apply regardless of desired speed |
| Policy Engine | Whether a proposed action is authorized in the current context |

Routes do not contain implementation prompts. Modes may reference versioned agent-role contracts and context recipes, but the orchestration engine remains responsible for dispatch.

## 3. Route Definition

A Route Definition contains:

- stable ID and semantic version;
- title, purpose, and supported use cases;
- entry criteria;
- ordered Stage specifications;
- allowed Stage transitions;
- required, conditional, and optional Mode rules per Stage;
- Gate requirements;
- mandatory controls;
- default Posture;
- allowed Postures;
- completion outcomes;
- and permitted tailoring operations.

### 3.1 Mode requirements

Each Stage classifies Mode participation as:

- `required`: always selected;
- `conditional`: selected when all declared predicates match;
- `optional`: may be selected by the Project Lead with a recorded rationale.

Required Modes cannot be removed from a Route Instance unless the Route explicitly marks them waivable and the applicable Policy permits a waiver.

### 3.2 Condition language

The bootstrap condition language is intentionally limited.

Each conditional rule contains `whenAll`, an array of predicates. A predicate references a named, typed project fact and uses exactly one supported comparison:

- `equals`
- `in`

Example:

```json
{
  "modeId": "MODE-UI-PROTOTYPE",
  "requirement": "conditional",
  "whenAll": [
    {"fact": "userFacing", "equals": true},
    {"fact": "maturityTarget", "in": ["prototype", "mvp", "production"]}
  ]
}
```

No arbitrary expressions, scripts, shell commands, or model-authored executable conditions are permitted.

## 4. Mode Contract

A Mode Contract contains:

- stable ID and semantic version;
- objective and non-goals;
- supported Stages;
- required inputs;
- participating roles;
- permission profile;
- permitted and prohibited shortcuts;
- required outputs;
- evidence requirements;
- completion criteria;
- default attempt budget;
- Posture-specific adjustments;
- possible outcomes;
- and allowed next Modes.

### 4.1 Mode execution grammar

Modes use a common outer grammar while defining their own internal work:

```text
PREPARE → ACT → COLLECT EVIDENCE → EVALUATE → OUTCOME
                         │
                         └── bounded repair or replanning
```

A Mode Contract does not claim that every Mode produces code. Investigation may produce findings; Experiment may produce accepted negative learning; Independent Review may produce findings; Monitoring may produce an operational event.

### 4.2 Posture adjustments

Posture changes permitted parameters, not the meaning of success.

Examples:

- Explore may allow more competing attempts with lighter artifact polish.
- Fast may narrow evidence to the core path while keeping hard controls.
- Balanced uses the Mode defaults.
- Assured expands review, traceability, and evidence.
- Emergency shortens checkpoints and creates mandatory follow-up work.

Posture may not remove a hard control inherited from Route, Risk Profile, Project policy, or organizational policy.

## 5. Route tailoring

The Project Lead may perform only the tailoring operations allowed by the Route Definition.

Initial operations:

- add an optional or conditional Mode;
- repeat a Stage;
- return to an earlier Stage;
- split a Unit;
- add an integration Stage or Gate;
- adjust Posture within the allowed set;
- narrow scope;
- and propose a different Route.

Removing required work, weakening controls, widening scope, changing the promotion target, or accepting risk requires the separate authority defined by policy.

Every tailored Route Instance records:

- base Route Definition and version;
- changes from the base;
- triggering Evidence or Learning;
- authorizing policy or Decision;
- effective time;
- and superseded Route Instance, if any.

## 6. Contract loading and validation

Contracts are loaded from version-controlled JSON files and validated before selection.

Validation fails closed when:

- an ID or version is missing;
- an unknown Stage, Posture, role, outcome, or requirement type appears;
- a conditional rule has no predicate;
- a predicate uses unsupported operators;
- a Route references a missing Mode;
- a required Mode does not support the Stage that activates it;
- no completion outcome is defined;
- a hard control has no stable identifier;
- or duplicate Stage or Mode rules create ambiguity.

Model output may propose contract changes, but only validated, version-controlled contracts can govern execution.

## 7. Mode selection

For a current Stage, the selection engine:

1. loads and validates the Route Definition;
2. loads and validates every referenced Mode Contract;
3. selects all required Modes;
4. evaluates conditional rules against authoritative facts;
5. adds optional Modes explicitly selected by an authorized decision;
6. verifies that every selected Mode supports the Stage;
7. combines Route, Risk, Project, and organizational controls;
8. applies Posture adjustments that do not weaken hard controls;
9. emits a selection explanation and input manifest.

The output is deterministic for the same contract versions, authoritative facts, optional selections, and policy bundle.

## 8. Initial Route library

The planned governed library contains:

1. Feasibility
2. Technical Proof
3. UX-First
4. MVP
5. Production-Ready
6. Brownfield Enhancement
7. Recovery
8. Emergency Delivery

The bootstrap implementation includes two representative Routes:

- Production-Ready, to exercise a full multi-stage path;
- Feasibility, to exercise learning-focused completion without production assumptions.

Additional Routes should be added only after their differences are represented by meaningful contract rules rather than by duplicated prose.

## 9. Initial Mode library

The bootstrap implementation includes:

- Investigation
- Architecture
- UI Prototyping
- Independent Review
- Hardening

This set exercises non-code outputs, conditional selection, user-facing design, role independence, and production-readiness controls.

## 10. Control inheritance

Effective controls are the union of applicable controls from:

```text
organization
  ∪ project
  ∪ route
  ∪ workstream
  ∪ unit risk profile
  ∪ stage
  ∪ mode
  ∪ target environment
```

Conflicting controls resolve to the stricter requirement unless a higher-authority policy explicitly defines another resolution.

Controls are identified by stable IDs. Human-readable labels alone are not sufficient for enforcement.

## 11. Explainability

Every selection result must explain:

- which Route and version governed;
- which Stage was evaluated;
- which Modes were selected;
- whether each Mode was required, conditional, or optional;
- which authoritative facts caused conditional selection;
- which controls were inherited;
- which Posture adjustments applied;
- and why excluded Modes were not selected when they were evaluated.

The liaison converts this into layman's terms when it affects the user. Internal rule IDs may be included as supporting detail but never replace the explanation.

## 12. Versioning

Route and Mode contracts use semantic versions.

- Patch: clarification or validation fix that does not change governed outcomes.
- Minor: backward-compatible addition such as a new optional Mode or output field.
- Major: changed required Mode, Stage transition, Gate, control, or completion semantics.

Every Route Instance and Agent Run records exact contract versions. In-progress Bolts do not automatically adopt a new major version.

## 13. Acceptance criteria

V3.1-ARCH-03 is acceptable when:

1. Route and Mode have separate machine-readable contracts.
2. Required, conditional, and optional Modes are unambiguous.
3. Conditions use a constrained, deterministic language.
4. Required Mode references are validated against the Mode library and Stage support.
5. Posture can adjust execution without weakening hard controls.
6. Route tailoring is explicit, attributable, and bounded.
7. A selection result explains why each Mode was or was not activated.
8. Production-Ready and Feasibility Routes validate as meaningfully different paths.
9. Representative Mode contracts validate and can be selected deterministically.
10. Invalid contracts fail closed before they govern execution.
