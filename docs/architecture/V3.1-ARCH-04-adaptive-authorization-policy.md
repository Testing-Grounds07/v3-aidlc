# V3.1-ARCH-04: Adaptive Authorization Policy

**Status:** Proposed architecture baseline  
**Version:** 0.1  
**Date:** 2026-09-16  
**Depends on:** V3.1-ARCH-01, V3.1-ARCH-02, V3.1-ARCH-03

## 1. Purpose

This specification defines how V3-AIDLC decides whether the Project Lead may take an action without interrupting the user.

In plain terms, the framework should keep routine work moving, keep a durable record when judgment is exercised, pause when a delegated limit is reached, ask the user when the requested outcome or real-world consequences would materially change, and refuse actions that violate a mandatory control or lack required permission.

Authorization is evaluated separately from lifecycle selection:

- Route and Mode contracts determine what work is appropriate.
- Authorization policy determines who may approve the next action.
- The Project Lead proposes and executes authorized actions.
- The liaison explains decisions and asks the user for input in layman's terms.

## 2. Authorization outcomes

| Machine outcome | Layman's meaning | Required behavior |
|---|---|---|
| `auto_proceed` | This is routine, reversible work already covered by the user's goal. | Continue without interrupting. |
| `auto_proceed_and_record` | The framework may decide, but the decision must be traceable. | Record the reason, affected scope, and governing rule before continuing. |
| `auto_proceed_within_budget` | The framework may continue only while an explicit limit remains. | Check the current attempt, time, or cost fact; record consumption. |
| `user_decision_required` | This decision belongs to the user or an explicitly delegated human authority. | Pause the affected branch and ask a concrete question with consequences. |
| `blocked` | The action is not allowed in the current context. | Do not execute; explain the unmet control or permission. |

These are authority outcomes, not workflow states. For example, a repair can receive `auto_proceed_within_budget`; a replan can receive `auto_proceed_and_record`.

## 3. Policy inheritance and precedence

Applicable policy can come from:

```text
organization → project → route → workstream → mode → target environment
```

All matching rules are evaluated. The strictest result wins:

```text
blocked
  > user_decision_required
  > auto_proceed_within_budget
  > auto_proceed_and_record
  > auto_proceed
```

Rule priority orders equally strict explanations; it never makes a permissive rule override a stricter one. A lower scope may add restrictions but cannot silently weaken inherited controls. An explicit, authorized policy version is required to change that behavior.

If no rule matches, the strictest applicable default is used. The governed baseline defaults to `user_decision_required`. Unknown action types therefore fail closed instead of being treated as routine work.

## 4. Action context

Before evaluation, the Project Lead creates an action context from authoritative state. It includes only facts needed by policy, such as:

- action type;
- affected scope and whether the action narrows, preserves, or expands it;
- reversibility and external impact;
- target environment;
- production credential use and standing delegation;
- whether product intent changes;
- whether residual risk is being accepted;
- whether a hard control would be waived;
- required permission availability;
- current repair attempt, cost, time, or other budget consumption;
- governing Route, Modes, Posture, and risk profile;
- evidence and Gate state relevant to the action.

Missing facts never count as permission. If a matching budget rule cannot verify consumption, the action requires a user decision.

## 5. Standing authority

The baseline gives the Project Lead standing authority for:

- routine local implementation within the approved intent and scope;
- tests, analysis, documentation, and evidence collection;
- reversible local changes;
- choosing among already-authorized implementation details;
- bounded repair while all declared budgets remain;
- replanning that preserves or narrows the approved outcome;
- permitted Route tailoring that preserves or narrows scope and is recorded;
- dispatching eligible Work Packages;
- accepting deterministic verification results;
- and continuing to the next eligible action after required records are written.

Standing authority is not inferred merely because an AI can perform an action. Capability and authorization are separate.

## 6. Decisions reserved for the user

Unless a specific standing delegation says otherwise, the affected work pauses for the user when an action would:

- materially change product intent or expected behavior;
- expand approved scope;
- create an irreversible external effect;
- accept material residual risk;
- exceed an attempt, time, cost, or other delegated budget;
- promote to production;
- use production credentials;
- change a promised delivery target or meaningful tradeoff;
- expose data to a new party or purpose;
- incur a significant external commitment;
- or repeat a failure after the configured repair and replan paths are exhausted.

The Project Lead should not escalate an entire project when only one branch is affected. Independent work continues when its policies and dependencies allow it.

## 7. Blocked actions

An action is blocked, rather than merely escalated, when execution would:

- bypass or silently waive a hard control;
- require a permission or capability that is unavailable;
- violate an applicable law, organizational prohibition, or target-environment rule;
- rely on an invalid or unversioned governing contract;
- use an unapproved secret or identity;
- or proceed despite evidence that its preconditions are false.

A user request can resolve a missing choice, provide permission, or authorize a policy change. It does not automatically erase a non-waivable control.

## 8. Budgeted autonomy

Budgets turn open-ended autonomy into bounded authority. A rule identifies an authoritative numeric fact and its maximum. Common dimensions include:

- repair attempts;
- elapsed time;
- compute or service cost;
- number of competing experiments;
- files, components, or interfaces affected;
- and tolerated operational exposure.

The evaluator checks current consumption before authorizing the action. Going above the maximum produces `user_decision_required`. A missing or non-numeric budget fact also escalates because the framework cannot prove that authority remains.

Budget replenishment, enlargement, or reset must be traceable to policy, a new Stage or Mode instance, or a human Decision. Retrying under a new label does not reset a budget.

## 9. Standing delegations

The user may establish a durable delegation, such as allowing production deployment after named Gates pass. A valid standing delegation records:

- who granted it;
- exact action types and targets it covers;
- preconditions and required evidence;
- limits and expiry, if any;
- revocation state;
- policy version that interprets it;
- and the Decision or conversation event that created it.

The liaison may translate conversational permission into a proposed delegation, but the Project Lead records the normalized form. Ambiguous conversation does not create standing authority.

## 10. Evaluation algorithm

For each proposed action, the policy engine:

1. verifies that at least one valid policy is available;
2. assembles authoritative action facts;
3. loads applicable policy versions from every scope;
4. evaluates the constrained `equals` and `in` predicates;
5. evaluates declared budgets for matching budgeted rules;
6. converts exhausted or unverifiable budgets to `user_decision_required`;
7. selects the strictest matched decision;
8. records all matches and identifies controlling rules;
9. emits a plain-language explanation;
10. returns the decision to the Project Lead before any side effect occurs.

Arbitrary scripts, model-authored executable expressions, and unrecorded exceptions are not permitted in policy predicates.

## 11. Records and auditability

Every non-routine decision records:

- action ID and action facts;
- policy IDs and exact versions;
- every matched rule;
- controlling rule or rules;
- budget values, if applicable;
- final authorization outcome;
- plain-language explanation;
- authorizing Decision or delegation, when human authority is used;
- and resulting event or blocked state.

Routine `auto_proceed` actions may be summarized at the Work Package level rather than generating a separate user-facing message. They remain observable through normal execution events.

## 12. Liaison behavior

When a user decision is required, the liaison:

- explains the decision in everyday language;
- says what is blocked and what can continue;
- presents the smallest concrete choice needed;
- explains meaningful consequences and tradeoffs;
- recommends an option when evidence supports one;
- and avoids internal state names or policy IDs unless they help the user verify the reasoning.

The liaison does not approve on the user's behalf, mutate canonical state independently, or become a second Project Lead. It passes the user's response back as a candidate Decision or delegation for normalization and recording.

## 13. Relationship to Posture

Posture may tune budgets and how often decisions are recorded, but it does not reverse the authority hierarchy.

- Explore can allow more experiments within a sandbox.
- Fast can shorten repair budgets and checkpoints.
- Balanced uses standard limits.
- Assured can require additional human or independent review.
- Emergency can use pre-authorized emergency actions with mandatory follow-up.

No Posture may silently permit a hard-control waiver, unavailable permission, or unapproved irreversible effect.

## 14. Bootstrap implementation

The initial implementation provides:

- `schemas/authorization-policy.schema.json`, the interchange contract;
- `policies/governed-development.json`, the baseline rule bundle;
- `v3_aidlc.authorization`, deterministic validation and evaluation;
- strictest-rule inheritance;
- bounded repair using attempt and cost facts;
- fail-closed defaults and missing-budget handling;
- and tests for routine work, material changes, hard controls, budgets, defaults, and stricter project policy.

The bootstrap policy is illustrative and governed. Production adopters should add organization-specific actions, permissions, limits, and non-waivable controls through versioned policies rather than source-code exceptions.

## 15. Acceptance criteria

V3.1-ARCH-04 is acceptable when:

1. Lifecycle selection and authorization are separate decisions.
2. Five authorization outcomes have distinct executable meanings.
3. Applicable policies inherit across scopes and the strictest matching rule wins.
4. Unknown actions and missing budget facts fail closed.
5. Routine reversible work can continue without unnecessary user interruption.
6. Repair and other repeated actions are constrained by explicit budgets.
7. Material intent changes, scope expansion, irreversible effects, risk acceptance, and undelegated production actions return to the user.
8. Hard-control waivers and missing permissions are blocked.
9. Standing delegations are explicit, bounded, revocable, and traceable.
10. Every governed result explains which policy rules controlled it.
11. The liaison can translate escalations into layman's terms without becoming an authority source.
12. Representative machine-readable policy and deterministic tests pass.
