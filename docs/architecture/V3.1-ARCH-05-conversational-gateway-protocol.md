# V3.1-ARCH-05: Conversational Gateway Protocol

**Status:** Proposed architecture baseline  
**Version:** 0.1  
**Date:** 2026-09-16  
**Depends on:** V3.1-ARCH-01 through V3.1-ARCH-04

## 1. Purpose

This specification defines how the main AI in a chat session works with V3-AIDLC when the user does not invoke the framework directly.

The main AI acts as a liaison. It recognizes when a request would benefit from managed project execution, preserves what the user actually said, proposes a normalized intake to the Project Lead, relays questions and decisions, and explains progress in ordinary language.

The liaison is not another Project Lead. It does not independently plan the project, approve governed actions, claim that decisions were recorded, or maintain a competing copy of project state.

## 2. The three actors

| Actor | Responsibility | Must not do |
|---|---|---|
| User | Defines desired outcomes, constraints, corrections, decisions, and delegations. | Learn framework terminology to receive useful service. |
| Liaison | Makes the framework accessible through normal conversation and faithfully relays meaning. | Become the source of truth or silently create authority. |
| Project Lead | Owns orchestration, canonical state, governed decisions, and execution receipts. | Treat the liaison's interpretation as unquestionable user intent. |

Only the Project Lead writes canonical project state. The liaison sends proposals and receives receipts.

## 3. When the liaison activates V3-AIDLC

The liaison keeps simple, self-contained questions conversational. It begins managed intake when one or more authoritative facts indicate that the work:

- was explicitly requested as V3-AIDLC work;
- must persist across sessions;
- needs coordinated stages, agents, or parallel workstreams;
- may create governed external effects;
- or is both multi-step and expected to create a durable artifact.

When a request names an existing managed project, the liaison attaches to that project instead of creating another. When multiple projects could own the work, it asks one focused identity question before attaching.

Activation is routing, not permission. Entering managed work does not authorize side effects, expand the user's goal, or create a standing delegation.

## 4. Invisible convenience, visible consequences

The user should not need to say “use V3,” select internal Modes, understand state names, or copy messages between agents. The liaison may perform routine routing without interrupting.

The liaison must become explicit when framework behavior affects the user, including:

- a material assumption;
- a choice that changes scope, timing, cost, risk, or product behavior;
- blocked work;
- requested authority or delegation;
- a meaningful plan change;
- or completion and remaining limitations.

The framework may be invisible as plumbing, but its consequences must not be hidden.

## 5. Intake handoff

The liaison creates an intake proposal containing:

- the user's verbatim request;
- requested outcome in normalized language;
- known constraints and non-goals;
- referenced artifacts and project identity;
- urgency or timing stated by the user;
- assumptions, clearly labeled as assumptions;
- unresolved ambiguity;
- requested side effects;
- and the conversation and message IDs needed for traceability.

The verbatim request is preserved alongside the summary. This prevents a convenient paraphrase from replacing the user's actual words.

The Project Lead may accept the intake, attach it to existing Intent, request clarification, identify a policy decision, or reject the proposed project association. Its response includes the recorded project reference and event receipt when state changes.

## 6. Message envelope

Every gateway handoff uses a versioned envelope with:

- schema version;
- stable message ID;
- conversation ID;
- optional project ID;
- source-message correlation ID;
- message kind;
- sender and recipient;
- timestamp;
- and a typed payload.

Direction is part of the contract. For example, `decision_needed` can only travel from Project Lead to liaison, while `decision_request` can only travel from liaison to user.

Messages with a correlation ID must reference an earlier message in the same conversation. Duplicate message IDs fail validation.

## 7. Relay pairs

| Source | Liaison relay |
|---|---|
| User request | Intake proposal to Project Lead |
| Project Lead clarification needed | Plain-language clarification request to user |
| User clarification | Clarification submission to Project Lead |
| Project Lead progress | Plain-language progress update to user |
| Project Lead decision needed | Plain-language decision request to user |
| User decision | Decision submission to Project Lead |
| Project Lead blocked result | Plain-language blocked notice to user |
| Project Lead completion | Plain-language completion report to user |
| User correction | Correction submission to Project Lead |
| User delegation | Bounded delegation proposal to Project Lead |
| User revocation | Revocation submission to Project Lead |

The liaison may reorganize and simplify explanations, but it must preserve verbatim requests, decisions, corrections, delegations, and revocations in their corresponding handoffs.

## 8. User-facing message contract

Every user-directed message includes four plain-language fields:

1. **Headline:** What happened or what choice is needed.
2. **Explanation:** What it means in familiar terms.
3. **Impact:** What changes for the user or project.
4. **Action needed:** What the user needs to do, including “nothing right now.”

A decision request also includes:

- one focused question;
- two to four meaningfully different options;
- the tradeoff of each option;
- and a recommendation when the evidence supports one.

Internal IDs and terms such as Work Package, Bolt, Route Instance, Posture, canonical state, and policy predicate do not appear in the primary explanation. They may appear in optional technical details when useful for verification.

Plain language does not mean hiding uncertainty or oversimplifying consequences. It means explaining them without requiring the user to understand the framework first.

## 9. Authority preservation

The liaison treats user responses as candidate governed input until the Project Lead records them.

Therefore:

- a user decision becomes a `decision_submission`, not a completed Decision;
- conversational permission becomes a `delegation_proposal`, not standing authority;
- a correction becomes a proposed state change;
- a revocation takes priority over queued but unexecuted delegated actions;
- and a Project Lead receipt confirms what was actually recorded.

Liaison-to-Project-Lead messages may not claim canonical event IDs, Decision IDs, recorded status, or canonical state. Those fields can only originate from the Project Lead.

## 10. Clarification behavior

The liaison asks only when missing information materially changes the result or authorization. It should:

- ask the smallest answerable question;
- provide sensible options when the answer space is known;
- state the assumption it would otherwise make;
- say what can continue while waiting;
- and avoid asking for information that canonical state already contains.

The Project Lead pauses only the affected branch. Other eligible work may continue under ARCH-04 authorization rules.

## 11. Corrections, revocations, and interruption

A new user message may correct, add to, or replace prior direction.

The liaison preserves the exact correction and indicates which prior message it appears to affect. The Project Lead determines the affected project entities, prevents new work under superseded direction, and records replanning or cancellation.

Revocation messages are high priority. Once received, the liaison immediately forwards them. The Project Lead stops dispatching actions that depend on the revoked authority and determines whether any already-started external action can safely be stopped or compensated.

The liaison never promises that an already-completed irreversible action was undone.

## 12. Progress and completion

Progress messages are event-driven rather than constant narration. The liaison reports when:

- a meaningful milestone completes;
- user input is needed;
- the plan materially changes;
- work is blocked;
- a substantial risk emerges;
- or the requested outcome completes.

A completion report distinguishes:

- what was delivered;
- what evidence supports completion;
- what changed from the original request;
- known limitations or remaining work;
- and the next useful action, if any.

The liaison must not report completion based only on an agent's claim. It uses the Project Lead's accepted evidence and completion receipt.

## 13. Failure and recovery

If the gateway cannot validate a message, loses correlation, or receives a response for an unknown project, it fails closed:

- do not invent state;
- preserve the original user message;
- retry only safe transport failures;
- ask the Project Lead to reconcile from canonical state;
- and explain any user-visible delay without exposing unnecessary internals.

After a chat interruption or new session, the liaison uses the project reference to request a fresh Project Lead summary. Conversation memory can help locate the project; it does not replace canonical state.

## 14. Privacy and context minimization

The liaison sends the minimum context needed for the Project Lead to act correctly. It distinguishes:

- user-provided facts;
- canonical project facts;
- liaison-derived summaries;
- assumptions;
- and unverified external information.

Sensitive conversation content is not copied wholesale when a narrower excerpt or reference is sufficient. Required verbatim authority statements are preserved because their exact wording affects governance.

## 15. Bootstrap implementation

The initial implementation provides:

- a versioned gateway protocol contract;
- a JSON envelope schema;
- deterministic activation routing from explicit facts;
- allowed actors, message kinds, and directions;
- validated relay pairings and correlations;
- preservation of verbatim authority-bearing language;
- a structured user-facing message contract;
- separation of internal identifiers from primary explanations;
- and a prohibition on liaison-authored canonical receipts.

The implementation validates protocol structure. Natural-language quality still requires review and future evaluation fixtures; the validator intentionally does not pretend that a keyword list can fully judge whether prose is understandable.

## 16. Acceptance criteria

V3.1-ARCH-05 is acceptable when:

1. A user can receive managed V3-AIDLC service without invoking the framework directly.
2. Simple conversational requests are not unnecessarily converted into projects.
3. Existing projects are attached rather than duplicated.
4. Ambiguous project identity produces one focused clarification.
5. The liaison preserves verbatim user intent and authority-bearing language.
6. Message kinds, actors, directions, correlations, and payloads are validated.
7. Only the Project Lead can produce canonical Decision and event receipts.
8. User-facing messages explain outcome, meaning, impact, and action needed in layman's terms.
9. Decision requests contain bounded options and evidence-supported recommendations.
10. Corrections and revocations are relayed without being silently reinterpreted.
11. Gateway failures reconcile from canonical state rather than conversation memory.
12. Representative protocol and relay tests pass deterministically.
