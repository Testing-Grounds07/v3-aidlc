# V3.1-ARCH-02: Project Lead Execution Loop

**Status:** Proposed architecture baseline  
**Version:** 0.1  
**Date:** 2026-09-16  
**Depends on:** V3.1-ARCH-01  

## 1. Purpose

This specification defines how the persistent Project Lead turns durable V3-AIDLC state into continued, governed action.

The Project Lead is not a never-ending chat session and is not the principal coder. It is a logical role reconstructed from authoritative project state whenever a decision is required. It selects eligible work, chooses the applicable Stage and Modes, dispatches bounded Agent Runs, evaluates returned evidence, initiates routine repair, adapts the plan, and escalates only decisions outside delegated authority.

The execution loop must solve the primary weakness observed in v3-lite: the system described continuation as automatic while the main conversational AI still had to select and initiate most next steps.

## 2. Governing principles

1. **Durable state drives execution.** Conversation history may supply new user intent but never determines current project truth by itself.
2. **The Project Lead initiates routine work.** It does not wait for repeated `Continue` messages when policy already authorizes progression.
3. **The framework, not the model, enforces transitions.** Eligibility, budgets, permissions, leases, evidence requirements, and gate status are deterministic where possible.
4. **Agents receive bounded contracts.** A worker cannot broaden its own scope, permissions, risk tolerance, or completion criteria.
5. **Implementation and approval remain separate.** An Actor cannot provide its own independent semantic acceptance.
6. **Failure classification precedes repair.** Application, framework, test, infrastructure, evidence, ambiguity, and decision failures follow different paths.
7. **Repair is bounded.** Repeated attempts consume explicit budgets and become observable state.
8. **Learning may change the route.** The system may branch, repeat, return to an earlier Stage, or recommend stopping.
9. **Human attention is reserved for judgment.** Routine reversible mechanics proceed under durable authorization.
10. **Every action is attributable.** Selection, dispatch, tool use, evidence, decisions, and transitions produce durable events.

## 3. Logical components

| Component | Responsibility |
|---|---|
| Project Lead | Reconcile project state, choose next governed action, and maintain project coherence |
| Eligibility Engine | Determine which Work Packages or governance actions may run |
| Policy Engine | Return `PROCEED`, `PROCEED_WITH_RECORD`, `REPAIR_AUTOMATICALLY`, `REPLAN`, `ESCALATE`, or `BLOCK` |
| Scheduler | Lease eligible work while respecting dependencies, conflicts, and concurrency limits |
| Context Compiler | Build the smallest provenance-aware context required by the assigned role |
| Agent Runner | Execute a typed role contract through an available provider |
| Evidence Collector | Capture commands, outputs, diffs, traces, hashes, and provider metadata |
| Verification Engine | Run deterministic checks and evaluate evidence admissibility |
| Review Router | Create independent, context-isolated semantic reviews |
| Gate Engine | Evaluate Package, Bolt, Stage, Integration, Promotion, and Release Gates |
| State Kernel | Append events and materialize the current Project snapshot transactionally |
| Liaison Gateway | Exchange Project Briefs, user Intents, decisions, and plain-language escalations with the main AI |

## 4. Project Lead wake conditions

The Project Lead is invoked when one of the following occurs:

- a user submits or changes an Intent;
- a user records a decision or control request;
- a Work Package, Agent Run, check, review, or Gate changes state;
- a retry or time budget becomes available or expires;
- an external dependency or permission changes;
- a scheduled continuation trigger fires;
- an operational event requires diagnosis;
- or project state is recovered after interruption.

A wake does not imply that an Agent Run must be started. The correct result may be to wait, reconcile, generate a brief, escalate, or declare completion.

## 5. Execution loop

```text
WAKE
  ↓
LOAD AND VERIFY STATE
  ↓
RECONCILE EVENTS, LEASES, EVIDENCE, AND REPOSITORY FACTS
  ↓
IDENTIFY CANDIDATE ACTIONS
  ↓
EVALUATE ELIGIBILITY, POLICY, RISK, AND BUDGET
  ↓
SELECT NEXT ACTION(S)
  ├── dispatch work
  ├── run verification
  ├── request independent review
  ├── repair
  ├── replan or adapt route
  ├── wait for dependency
  ├── escalate decision
  └── complete project or checkpoint
  ↓
RECORD ACTION AND LEASE
  ↓
EXECUTE THROUGH BOUNDED ROLE CONTRACT
  ↓
COLLECT OUTPUTS AND EVIDENCE
  ↓
CLASSIFY RESULT
  ↓
EVALUATE CHECK OR GATE
  ↓
APPEND EVENTS AND UPDATE SNAPSHOT
  ↓
WAKE AGAIN WHEN CONTINUATION IS AUTHORIZED
```

The loop is event-driven. A chat turn may wake it, but a chat turn is not the unit of execution.

## 6. Project Lead run states

| State | Meaning |
|---|---|
| `sleeping` | No unprocessed wake condition exists |
| `reconciling` | Durable state is being compared with external facts and incomplete work |
| `selecting` | Eligible actions are being evaluated and prioritized |
| `dispatching` | A lease and bounded Agent Run contract are being created |
| `waiting` | Progress depends on a declared external event, dependency, or retry time |
| `evaluating` | Results, evidence, findings, or Gates are being assessed |
| `repairing` | An authorized bounded repair loop is active |
| `replanning` | A plan, Mode, Stage, Unit, or Route change is being prepared |
| `escalated` | A specific human decision or new authority is required |
| `paused` | The user or policy has suspended execution |
| `completed` | The governed Intent or selected checkpoint is complete |
| `blocked` | No authorized transition can currently resolve the condition |

Only the State Kernel may persist a Project Lead state transition.

## 7. Work Package states

| State | Meaning |
|---|---|
| `proposed` | Candidate work exists but has not been admitted to the plan |
| `planned` | Scope, outcome, dependencies, and evidence requirements are defined |
| `eligible` | Dependencies and policy permit scheduling |
| `leased` | One authorized runner temporarily owns execution |
| `running` | The assigned Actor or tool is performing work |
| `evidence_pending` | Execution ended but required evidence is incomplete |
| `verifying` | Deterministic checks are running or being evaluated |
| `reviewing` | Independent semantic review is active |
| `repair_required` | Findings are repairable inside current authority and budget |
| `replan_required` | The existing plan or assumptions are no longer adequate |
| `decision_required` | Human judgment or new authority is required |
| `blocked` | A dependency or non-authorized condition prevents progress |
| `accepted` | Package criteria and applicable checks have passed |
| `closed` | Accepted outcome and closeout were recorded transactionally |
| `cancelled` | Work was intentionally stopped with rationale |
| `superseded` | Another package or plan replaced this work |

`accepted` and `closed` are separate logical facts but should normally be persisted in one closeout transaction. A state-only pull request is not required merely to represent the transition.

## 8. Eligibility

A Work Package is eligible when all conditions are true:

```text
dependencies accepted or satisfied
AND required upstream artifacts stable
AND applicable Stage permits the Mode
AND Route Instance permits the transition
AND no exclusive conflict-domain lease exists
AND required tools and permissions are available
AND risk controls are satisfied
AND execution and cost budgets remain
AND the Project and parent Unit are not paused, cancelled, or blocked
```

Eligibility is recalculated from durable facts. The Project Lead may prioritize among eligible items but cannot declare an ineligible package eligible without a recorded governed change.

## 9. Selection and scheduling

The Project Lead orders eligible actions by:

1. mandatory safety or recovery action;
2. active critical-path dependency;
3. user-declared priority or deadline;
4. blocking integration work;
5. highest intent value unlocked;
6. lowest-cost uncertainty reduction;
7. normal planned order.

Parallel dispatch is permitted only when:

- packages have no unresolved dependency relationship;
- conflict domains do not overlap;
- required contracts are stable;
- integration responsibility is assigned;
- concurrency quotas permit it;
- and the expected coordination cost does not exceed the predicted benefit.

## 10. Dispatch contract

Every Agent Run receives an immutable dispatch contract containing:

- Project, Intent, Workstream, Unit, Stage, Mode, Bolt, and Work Package IDs;
- objective and non-goals;
- allowed files, resources, tools, and network destinations;
- prohibited changes and actions;
- applicable requirements, decisions, and architecture constraints;
- expected outputs;
- required verification and evidence;
- attempt and cost budgets;
- termination conditions;
- escalation rules;
- and the exact context-manifest ID.

The runner may return a proposed scope change, but it cannot authorize that change itself.

## 11. Result classification

Before deciding what to do next, the system classifies the primary result:

| Classification | Typical examples | Default response |
|---|---|---|
| `application_defect` | Incorrect implementation or regression | Bounded repair |
| `framework_defect` | Invalid guard, state mismatch, scheduler error | Pause affected orchestration; repair framework |
| `test_or_oracle_defect` | Incorrect fixture, stale expectation, false positive | Independently validate and repair test system |
| `infrastructure_failure` | CI outage, missing daemon, transient network failure | Retry or choose an authorized equivalent environment |
| `evidence_failure` | Test ran but evidence is missing, stale, or bound to wrong revision | Recollect exact evidence; do not assume application failure |
| `requirement_ambiguity` | Several materially different interpretations | Replan or escalate depending authority |
| `product_decision` | Tradeoff changes behavior, value, or commitment | Escalate with recommendation |
| `negative_learning` | Experiment disproves an approach | Accept Learning and adapt plan |
| `inconclusive` | Budget exhausted without a reliable conclusion | Replan, escalate, or stop explicitly |
| `accepted_result` | Criteria and evidence satisfied | Evaluate Gate and close |

Classifications may be revised when new evidence appears. The revision must be recorded rather than overwriting history.

## 12. Bounded repair

A repair loop may proceed automatically when:

- the issue is inside the approved objective and change surface;
- the action is reversible;
- risk does not increase beyond policy;
- no product decision is hidden inside the repair;
- the repair budget remains;
- and independent acceptance remains possible.

The default bootstrap budget is three related repair attempts per finding cluster. Route, Mode, Posture, and Risk Profile may set stricter or more generous limits.

Each repair attempt records:

- classification;
- hypothesis;
- changes made;
- evidence collected;
- outcome;
- remaining budget;
- and whether the same failure signature recurred.

Repeated equivalent failures trigger `REPLAN` or `ESCALATE`; they must not consume unbounded agent runs.

## 13. Replanning and adaptive changes

The Project Lead may automatically replan within policy when it changes implementation tactics but preserves:

- Intent;
- user-visible acceptance criteria;
- risk tolerance;
- material scope;
- operating cost boundary;
- promotion target;
- and mandatory controls.

The Project Lead may propose, but not silently perform, changes to those protected elements.

Adaptive changes include:

- activating an additional Mode;
- returning a Unit to an earlier Stage;
- splitting or combining Units;
- revising Bolt composition;
- changing package dependencies;
- selecting an alternate permitted environment;
- or recommending a different Route.

Every adaptation records its triggering Evidence or Learning.

## 14. Escalation contract

An escalation must contain:

- a stable decision ID;
- plain-language description of what happened;
- why it matters;
- realistic options;
- the Project Lead's recommendation;
- consequences of each option;
- urgency and default safe behavior while waiting;
- technical evidence references;
- and the exact response needed.

The Project Lead must not escalate a routine implementation choice merely because several valid tactics exist. It should select the best policy-compliant tactic and record the choice.

## 15. Liaison interaction

The liaison receives structured Project Lead outputs and communicates with the user in layman's terms.

The liaison does not decide package eligibility or reconstruct status from chat history. It requests a current `project.brief` and translates it.

Default status reports answer:

1. Where are we?
2. What finished?
3. What is happening now?
4. Did anything go wrong?
5. Was it handled automatically?
6. Does the user need to do anything?
7. What happens next?

When a user grants durable authority, the liaison submits a policy change rather than treating the statement as permission limited to the current chat turn.

## 16. Reconciliation and interruption recovery

At every recovery wake, the Project Lead compares durable state with:

- repository branch and commit facts;
- active and expired leases;
- provider run status;
- CI status;
- evidence existence and hashes;
- open review findings;
- and parent Gate state.

Possible reconciliation outcomes:

- resume an active authorized run;
- expire and redispatch a stale lease;
- accept externally completed work after normal verification;
- classify an orphaned result;
- repair state projection from the event ledger;
- or escalate an irreconcilable conflict.

The Project Lead never infers completion solely because a conversational agent previously claimed success.

## 17. Transaction boundaries

The following operations must be atomic from the Project's perspective:

### Dispatch

```text
confirm eligibility
→ create lease
→ create Agent Run
→ append dispatch event
→ update materialized snapshot
```

### Accepted closeout

```text
bind admissible evidence
→ record findings disposition
→ record Gate Decision
→ mark Work Package accepted and closed
→ release lease/conflict domains
→ update parent Bolt/Unit readiness
→ append closeout events
→ update materialized snapshot
```

### Escalation

```text
record blocked transition
→ create Decision Request
→ establish safe waiting behavior
→ append escalation event
→ update Project Brief
```

Generated repository summaries may follow these transactions; they are not the state authority.

## 18. Stale-state safeguards

Before dispatch, merge, Gate acceptance, or Project Brief generation, the framework must verify that:

- the snapshot includes the latest committed event;
- referenced evidence exists and matches its hash;
- repository evidence is bound to the intended revision;
- no conflicting lease exists;
- and the Work Package state permits the requested transition.

If a generated snapshot disagrees with the event ledger, the snapshot is regenerated. The event ledger is not edited to match the snapshot.

## 19. Project completion

An Intent may be declared complete when:

- its applicable success measures are satisfied or explicitly disposed;
- required Units have crossed their target Gates;
- unresolved risks and deferred work are visible;
- operational ownership is established when applicable;
- and the completion authority required by policy has approved.

Completion reports distinguish:

- delivered capability;
- validated learning;
- deferred scope;
- known limitations;
- unvalidated assumptions;
- and recommended next routes.

## 20. Machine-readable transition contract

The initial implementation shall provide a deterministic transition model for Project Lead and Work Package states. Invalid transitions fail closed and return the set of permitted next states.

The transition model is a framework fact, not a prompt instruction.

## 21. Acceptance criteria

V3.1-ARCH-02 is acceptable when:

1. A wake condition can be processed without relying on conversation history.
2. Work eligibility is calculated from durable dependencies, policy, risk, permissions, budgets, and conflict domains.
3. Routine authorized work continues without a repeated user prompt.
4. Project Lead and Work Package states have deterministic allowed transitions.
5. Dispatch and closeout have explicit transaction boundaries.
6. Application, framework, test, infrastructure, evidence, ambiguity, and decision failures produce different default responses.
7. Repair loops have visible budgets and termination behavior.
8. Replanning distinguishes tactical adaptation from protected product changes.
9. Independent review remains required where the applicable Route and Gate demand it.
10. Escalations are understandable in layman's terms and contain actionable options and a recommendation.
11. Interrupted work can be reconciled against repository, provider, CI, lease, and evidence facts.
12. Snapshot drift cannot override the event ledger.
