# V3.1-ARCH-01: Adaptive Lifecycle Domain Model

**Status:** Proposed architecture baseline  
**Version:** 0.1  
**Date:** 2026-09-16  
**Supersedes:** No existing V3 contract; extends the original V3 architecture and schema blueprint  

## 1. Purpose

V3.1 evolves V3 from a primarily fixed, stage-based agentic SDLC control plane into an adaptive AI-driven development control plane.

The framework must support several kinds of development inside the same project at the same time. One workstream may be exploring whether an idea is possible, another may be creating a high-resolution interface, another may be validating an MVP with users, and another may be hardening authentication for production. V3.1 must apply the appropriate workflow and level of assurance to each without losing project-level coherence.

The core principle remains unchanged:

> The Project Lead owns intent and project coherence. Planning agents propose. Action agents modify the world. Review and verification agents independently judge. Deterministic systems establish facts. Gates control transitions. Artifacts preserve institutional memory. Humans retain authority over consequential ambiguity and risk.

V3.1 adds a second principle:

> Routes define the journey. Workstreams divide the project. Stages locate the work. Stages activate modes. Modes generate bounded execution. Evidence determines whether work advances, repeats, branches, changes route, or stops.

## 2. Design goals

V3.1 shall:

1. Start from a user-defined Intent rather than assuming a software feature request.
2. Allow governed routes to be selected and adapted to the work.
3. Allow parallel workstreams to occupy different lifecycle stages.
4. Make modes executable playbooks rather than descriptive labels.
5. Adjust speed and assurance through a delivery posture without weakening mandatory risk controls.
6. Represent experiments, negative findings, and learning as valid outcomes.
7. Give the Project Lead enough authority to continue routine work without repeated user prompts.
8. Preserve independent review, deterministic verification, evidence binding, and traceability.
9. Support both greenfield and brownfield development.
10. Treat deployment, operation, maintenance, recovery, and retirement as part of the lifecycle.
11. Allow a main conversational AI to act as a plain-language liaison without becoming a competing source of project truth.
12. Measure verified intent-level value rather than agent activity or code volume.

## 3. Non-goals

This specification does not yet select:

- an orchestration programming language;
- SQLite, PostgreSQL, or another persistence engine;
- a queue or background-job system;
- a web-interface framework;
- a specific coding-agent provider;
- a vector database;
- or a deployment platform.

It also does not replace the existing V3 roles, evidence model, event ledger, Git history, provider isolation, or independent-review requirements.

## 4. Domain hierarchy

```text
Project
├── Intent
├── Route Instance
│   ├── Workstreams
│   │   └── Units
│   │       ├── Current Stage
│   │       ├── Required and Active Modes
│   │       ├── Delivery Posture
│   │       ├── Risk Profile
│   │       └── Bolts
│   │           └── Work Packages
│   │               └── Tasks / Agent Runs
│   └── Project-level Integration and Promotion Gates
├── Decisions and Learnings
├── Evidence and Findings
└── Releases and Operational Outcomes
```

The hierarchy is not a waterfall. A Unit can return to an earlier Stage, activate an additional Mode, split into new Units, or propose a Route change when evidence requires it.

## 5. Core entities

### 5.1 Project

The durable boundary for goals, authority, artifacts, state, evidence, repositories, workstreams, and operating policy.

A Project is the primary continuity container. Conversation history is never its source of truth.

### 5.2 Intent

A high-level statement of the outcome, question, or change a user wants.

An Intent may describe:

- a business or user outcome;
- a software capability;
- a technical outcome;
- an experiment or question;
- a repair;
- an operational improvement;
- or a retirement decision.

An Intent must include success measures or explicitly record that discovering suitable measures is part of the work.

### 5.3 Route Definition

A governed, reusable lifecycle pattern composed of:

- expected Stages;
- allowed transitions;
- required, conditional, and optional Modes;
- stage-entry and stage-exit rules;
- default evidence expectations;
- promotion gates;
- and route-specific escalation rules.

Initial Route Definitions:

1. Feasibility
2. Technical Proof
3. UX-First
4. MVP
5. Production-Ready
6. Brownfield Enhancement
7. Recovery
8. Emergency Delivery

### 5.4 Route Instance

The Project Lead's tailored application of a Route Definition to a specific Intent or Workstream.

The Project Lead may add, repeat, reorder, or conditionally skip permitted elements. It may not silently remove mandatory controls or required evidence.

### 5.5 Workstream

A continuing area of project activity that can progress partly independently while remaining connected to the same Project and Intent.

Examples include user experience, data ingestion, analysis, authentication, infrastructure, and operations.

A Workstream owns one or more Units and declares dependencies or integration points with other Workstreams.

### 5.6 Unit

A cohesive, relatively independent piece of capability, value, or learning derived from an Intent.

A Unit:

- has measurable completion or learning criteria;
- progresses through Stages;
- activates Modes;
- may be developed through one or more Bolts;
- and may be independently promoted, paused, split, combined, or retired.

### 5.7 Stage

The Unit's current position in its lifecycle.

Initial Stages:

1. Discovery
2. Definition
3. Design
4. Implementation
5. Validation
6. Release
7. Operation
8. Retirement

A Stage does not prescribe one fixed workflow. It activates the Modes required by the Route Instance, Posture, Risk Profile, Unit characteristics, and available evidence.

### 5.8 Mode

A reusable, executable way of working inside a Stage.

A Mode contract defines:

- objective;
- required inputs;
- agent roles;
- allowed tools and permissions;
- permitted and prohibited shortcuts;
- output artifacts;
- evidence obligations;
- completion criteria;
- repair or retry behavior;
- attempt budget;
- and possible next Modes or Stage transitions.

Initial Modes:

- Investigation
- Experiment
- Proof of Concept
- Requirements Development
- Architecture
- Domain Modeling
- Workflow Prototyping
- UI Prototyping
- Feature Development
- Integration
- Migration
- Automated Verification
- Independent Review
- Security Evaluation
- User Validation
- Pilot
- Hardening
- Deployment
- Monitoring
- Maintenance
- Recovery
- Optimization
- Retirement

### 5.9 Delivery Posture

The desired balance between learning speed, delivery speed, assurance, and urgency.

Initial Postures:

- **Explore:** Maximize learning and inexpensive comparison.
- **Fast:** Deliver the smallest useful result inside defined limits.
- **Balanced:** Balance speed, maintainability, and assurance.
- **Assured:** Maximize confidence, traceability, and operational readiness.
- **Emergency:** Minimize elapsed time while preserving non-bypassable safety controls and creating mandatory follow-up work.

Posture changes evidence depth, review breadth, attempt budgets, and checkpoint frequency. It cannot weaken applicable hard-risk controls.

### 5.10 Risk Profile

The set of risks, tolerances, and mandatory controls applying to a Project, Workstream, Unit, or Work Package.

At minimum, a Risk Profile evaluates:

- real or sensitive data;
- identity and authorization;
- destructive or irreversible actions;
- production access;
- financial, legal, regulatory, or physical consequences;
- external communication;
- user population and dependency;
- reversibility;
- and failure impact.

The narrowest object-specific Risk Profile inherits all stricter applicable controls from its parents.

### 5.11 Bolt

A short, focused build-and-validation cycle that advances a Unit.

A Bolt:

- has one coherent objective;
- contains one or more related Work Packages;
- may run sequentially or in parallel with independent Bolts;
- ends with a Bolt Check;
- and records outcomes, evidence, learning, and follow-up work.

Bolt duration is not fixed. The term describes bounded execution, not a promise that every question can be resolved in hours.

### 5.12 Work Package

A bounded, traceable assignment performed through one or more Tasks or Agent Runs.

The existing V3 Work Package contract remains valid and is extended with:

- `intentIds`
- `routeInstanceId`
- `workstreamId`
- `unitId`
- `boltId`
- `stageId`
- `modeId`
- `posture`
- `riskProfileId`
- `expectedOutcomeTypes`
- and `promotionTarget`

### 5.13 Evidence

Durable proof used to support a claim, finding, transition, or gate decision.

Evidence remains immutable or content-addressed where practical and separate from project belief or status.

### 5.14 Finding

An observed issue, discrepancy, risk, or improvement opportunity produced by verification or review.

Findings must distinguish at least:

- application defect;
- framework defect;
- test or oracle defect;
- infrastructure or provider failure;
- incomplete evidence;
- requirement ambiguity;
- and product decision.

### 5.15 Learning

A validated observation that changes or confirms project understanding.

A Learning can record:

- a supported hypothesis;
- a rejected approach;
- an inconclusive result;
- a revised assumption;
- a new requirement;
- a discovered constraint;
- or evidence supporting a Route or Mode change.

A negative experimental result may be a successful Mode outcome.

### 5.16 Gate

A policy-controlled decision about whether work may advance.

Gate levels:

1. Package Check
2. Bolt Check
3. Stage Gate
4. Integration Gate
5. Promotion Gate
6. Release Gate

Gate requirements are generated from Route, Stage, Mode, Posture, and Risk Profile. Deterministic failures and mandatory risk controls cannot be silently waived.

### 5.17 Promotion

An evidence-backed transition to a more demanding maturity or operating commitment.

Examples include proof of concept to prototype, prototype to MVP, MVP to pilot, and pilot to production operation.

Promotion creates a gap assessment and required hardening work; it never assumes that prototype shortcuts are already production-ready.

## 6. Relationships and invariants

1. Every active Unit traces to at least one Intent.
2. Every Unit belongs to one primary Workstream.
3. Every active Unit has exactly one current Stage.
4. A Unit may have multiple active Modes when the Route permits parallel work.
5. Every Bolt advances one Unit and declares its active Stage and Modes.
6. Every Work Package belongs to one Bolt unless explicitly classified as project-level integration or governance work.
7. Every Stage transition is supported by a Gate Decision or an explicit governed exception.
8. Every Gate Decision references admissible Evidence.
9. An implementing Agent Run cannot approve its own semantic or acceptance Gate.
10. Risk controls inherit downward and may become stricter, never silently weaker.
11. Conversational instructions that change scope, posture, route, or authority become durable Decisions or Policy events.
12. Project state is reconstructed from durable state and events, never inferred solely from conversation history.

## 7. Adaptive selection model

The Project Lead selects or updates a Route Instance using:

- Intent and success measures;
- current uncertainty;
- existing system maturity;
- user population;
- real versus simulated data;
- reversibility;
- delivery urgency;
- promotion target;
- dependencies;
- and Risk Profile.

The Project Lead selects Modes for a Stage using governed rules.

Example for the Design Stage:

```text
Always:
  establish the intended workflow or system behavior

Conditionally:
  activate UI Prototyping when users directly interact with the Unit
  activate Proof of Concept when technical feasibility is uncertain
  activate Experiment when alternatives must be compared
  activate Security Evaluation when identity or sensitive data is involved
  activate Domain Modeling when business rules are complex
  activate Integration when contracts cross Workstream boundaries
```

## 8. Outcome model

A Mode, Bolt, or Work Package may conclude with:

- Accepted Result
- Accepted Learning
- Repair Required
- Repeat Required
- Replan Required
- Route Change Proposed
- Promotion Proposed
- Blocked by Dependency
- Human Decision Required
- Abandoned with Evidence
- Inconclusive within Budget

Only `Repair Required` or a failed mandatory check necessarily represents failed execution. A rejected hypothesis can be an accepted learning outcome.

## 9. Authorization model

The Project Lead evaluates proposed actions using durable policy and returns:

- `PROCEED`
- `PROCEED_WITH_RECORD`
- `REPAIR_AUTOMATICALLY`
- `REPLAN`
- `ESCALATE`
- `BLOCK`

Routine implementation, testing, bounded repair, evidence recording, accepted merge, closeout, and next-work dispatch should proceed automatically when already authorized by Route, Posture, Risk Profile, and project policy.

Human escalation is reserved for:

- material Intent or product-direction change;
- meaningful scope expansion outside policy;
- high-consequence risk acceptance;
- irreversible external action;
- production credentials or access not already delegated;
- waiver of mandatory controls;
- significant new operating cost;
- unresolved repeated failure beyond budget;
- and promotion into a higher-consequence operating commitment when policy requires it.

## 10. Conversational liaison

Users may interact with V3 indirectly through the main AI in a chat session.

The main AI is a **liaison**, not a second Project Lead and not a source of project truth.

The liaison shall:

- identify the relevant Project;
- request a current Project Brief;
- translate natural-language user intent into structured project messages;
- return user decisions to the Project Lead;
- explain outcomes, impact, choices, and required actions in layman's terms;
- reveal technical detail progressively when useful or requested;
- and clearly state whether the user needs to do anything.

The liaison shall not independently reconstruct project state, choose the next Work Package, approve work, or override durable policy.

The Project Lead shall provide enough structured and explanatory context for the liaison to distinguish:

- an application defect;
- a framework defect;
- a test or evidence problem;
- an infrastructure problem;
- and a genuine user decision.

### 10.1 Plain-language communication contract

Default user-facing reports answer:

1. Where are we?
2. What was completed?
3. What is happening now?
4. What went wrong, if anything?
5. Was it handled automatically?
6. Does the user need to act?
7. What happens next?

Decision requests explain:

1. What happened?
2. Why does it matter?
3. What are the realistic choices?
4. What does the Project Lead recommend?
5. What happens after the user chooses?

Internal identifiers and framework terms may support an explanation but may not substitute for one.

### 10.2 Gateway message families

Liaison to Project Lead:

- `intent.submit`
- `intent.update`
- `decision.record`
- `project.status`
- `project.control`
- `user.preference.record`

Project Lead to liaison:

- `project.brief`
- `decision.request`
- `progress.event`
- `exception.report`
- `completion.report`
- `delegation.offer`

The Project Lead may assign bounded implementation work to the conversational AI. Such delegation must include scope, authority, prohibited changes, evidence obligations, and independent review requirements.

## 11. Greenfield and brownfield behavior

Greenfield Routes build progressively richer context from Intent through requirements, design, implementation, validation, and operation.

Brownfield Routes first activate a System Reconstruction Mode that produces:

- a static representation of components, responsibilities, and relationships;
- a dynamic representation of significant workflows;
- implementation-to-documentation discrepancies;
- affected contracts and risk boundaries;
- and a confidence-rated impact assessment.

Changes proceed only after the current system is understood sufficiently for the selected Posture and Risk Profile.

## 12. Persistence and traceability

V3.1 preserves the original separation among:

- materialized Project snapshot;
- append-only event ledger;
- versioned engineering artifacts;
- immutable evidence store;
- Git source history;
- and redacted provider execution records.

The artifact graph adds typed relationships for Intent, Route Instance, Workstream, Unit, Stage, Mode, Posture, Risk Profile, Bolt, Learning, and Promotion.

Required traceability paths include:

```text
Intent → success measure → Unit → requirement/design → Work Package
→ change → verification evidence → Gate Decision → release/operational result
```

and:

```text
Failure/finding → evidence → change/run → Work Package → Mode → Stage
→ Unit → Workstream → Intent
```

## 13. Migration from V3 and v3-lite

Existing records remain valid.

Default migration rules:

- Existing Project remains Project.
- Existing milestone or stage maps to the nearest V3.1 Stage with a recorded migration decision.
- Existing Work Package receives a generated parent Unit and Bolt when no natural parent exists.
- Existing autonomy setting becomes a Project authorization policy and default Posture recommendation.
- Existing evidence, findings, gates, attempts, and agent runs retain identity.
- Existing requirements and architecture decisions link to the generated or selected Intent.
- Missing Route, Workstream, Mode, Posture, and Risk values are marked `legacy-unclassified`; they are not silently invented.

Migration must preserve all prior hashes, evidence references, gate decisions, and audit history.

## 14. Evaluation requirements

V3.1 shall evaluate the harness at Agent Run, Work Package, Bolt, Unit, Workstream, and Project levels.

Initial adaptive-lifecycle metrics:

- verified Intent measures achieved;
- human decisions per accepted Unit;
- unnecessary human interruptions;
- autonomous continuation rate;
- time waiting for avoidable approval;
- repair attempts and repair success;
- route and mode changes caused by evidence;
- application versus framework versus infrastructure failure rate;
- evidence-production overhead;
- user-validation latency;
- promotion-gap accuracy;
- and longitudinal quality change.

The principal outcome is verified intent-level value per unit of human attention, elapsed time, cost, and accepted risk.

## 15. Initial route-stage-mode example

```text
Route: Production-Ready Application

Discovery
  Required: Investigation
  Conditional: Experiment, System Reconstruction

Definition
  Required: Requirements Development, Risk Assessment
  Conditional: Workflow Prototyping

Design
  Required: Architecture
  Conditional: Domain Modeling, UI Prototyping, Proof of Concept,
               Security Evaluation, Integration

Implementation
  Required: Feature Development, Automated Verification
  Conditional: Integration, Migration

Validation
  Required: Automated Verification, Independent Review
  Conditional: Security Evaluation, User Validation, Pilot

Release
  Required: Hardening, Deployment, Release Gate

Operation
  Required: Monitoring, Maintenance
  Conditional: Recovery, Optimization

Retirement
  Required: Retirement and preservation verification
```

## 16. Acceptance criteria for V3.1-ARCH-01

This architecture package is acceptable when:

1. Every new entity has a distinct purpose and defined relationship to existing V3 entities.
2. Route, Stage, Mode, Posture, and Risk Profile cannot be confused with one another.
3. Parallel Workstreams can occupy different Stages and activate different Modes.
4. Experiments and negative findings can complete successfully as Learning.
5. The Project Lead can continue routine work without repeated user authorization.
6. Mandatory controls remain enforceable regardless of Route or Posture.
7. Independent verification and review remain structurally separate from implementation.
8. Existing V3 and v3-lite records can be migrated without loss of evidence or audit history.
9. A main conversational AI can interact with the Project Lead through explicit contracts.
10. The liaison is required to communicate with the user in accurate layman's terms.

## 18. Open decisions

The following decisions are intentionally deferred:

- whether Unit and Workstream are both required in the smallest implementation;
- whether Bolts need durable first-class identity or can initially be grouped Work Package attempts;
- which Route Definitions are included in the first executable release;
- which Modes need independent specialist agents versus parameterized playbooks;
- the initial risk-classification scale;
- and the exact compatibility representation for v3-lite SQLite/JSON records.

These decisions should be resolved through V3.1-ARCH-02 and V3.1-ARCH-03 rather than guessed during implementation.
