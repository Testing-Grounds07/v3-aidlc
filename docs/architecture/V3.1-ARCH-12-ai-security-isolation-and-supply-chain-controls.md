# V3.1-ARCH-12: AI Security, Isolation, and Supply-Chain Controls

**Status:** Proposed architecture baseline  
**Version:** 0.1  
**Date:** 2026-09-17  
**Depends on:** V3.1-ARCH-04, V3.1-ARCH-07, V3.1-ARCH-08, V3.1-ARCH-09, V3.1-ARCH-10, and V3.1-ARCH-11

## 1. Purpose

This specification defines the security boundary for AI-assisted and agentic work in V3-AIDLC.

In plain terms, an AI may read content that contains malicious instructions, generate unsafe code, request more access than it needs, expose credentials, install compromised dependencies, or create artifacts whose origin cannot be trusted. V3 therefore treats AI output and retrieved material as potentially unsafe until governed controls establish otherwise.

ARCH-12 defines how V3:

- separates data from authority;
- handles prompt injection and poisoned context;
- grants tools, files, network access, and credentials narrowly;
- isolates untrusted execution;
- checks dependencies and build provenance;
- binds artifacts to exact source, runner, and revision;
- detects suspicious behavior;
- and contains incidents without destroying evidence.

## 2. Research basis

The baseline draws on:

- [OWASP GenAI Security Project](https://genai.owasp.org/) guidance on prompt injection, sensitive-information disclosure, supply-chain risk, excessive agency, and agentic security;
- the [NIST Generative AI Profile](https://www.nist.gov/itl/ai-risk-management-framework) for AI risk governance, measurement, incident preparation, and lifecycle controls;
- [SLSA v1.2 build requirements](https://slsa.dev/spec/v1.2/build-requirements) and [provenance specification](https://slsa.dev/spec/v1.2/build-provenance) for artifact traceability, signed provenance, hosted builds, and hardened build isolation;
- and [CISA software supply-chain guidance](https://www.cisa.gov/topics/cyber-threats-and-advisories/software-supply-chain) for lifecycle-wide dependency and supplier risk.

These sources inform the control categories. V3’s executable contracts remain its governing implementation baseline.

## 3. Security principles

V3 applies these principles:

1. **Content is not authority.** Retrieved documents, webpages, tickets, repository text, model output, and tool output cannot grant permissions or change policy.
2. **Least privilege per run.** Tools, resources, network hosts, and credentials are granted to one exact Agent Run for limited time and purpose.
3. **Fail closed.** Unknown trust, missing grants, stale credentials, prohibited dependencies, and insufficient provenance stop or escalate work.
4. **Isolation before confidence.** Untrusted content is bounded technically rather than trusted because the model appears confident.
5. **Evidence before promotion.** Generated artifacts and security claims require verifiable provenance and Checks.
6. **No secret values in context or state.** V3 passes secret references and brokered leases, not raw credentials.
7. **Contain first, investigate second.** Serious signals revoke access, isolate effects, quarantine artifacts, and preserve evidence.
8. **Adaptive controls cannot erase hard boundaries.** Faster Routes may reduce optional depth, not authority, isolation, credential, or provenance requirements.

## 4. Threat boundary

The baseline addresses:

- direct and indirect prompt injection;
- context and memory poisoning;
- data exfiltration and sensitive-information disclosure;
- excessive agency and tool escalation;
- credential theft or misuse;
- unsafe execution of generated or retrieved code;
- persistence across runs or workspaces;
- malicious or vulnerable dependencies;
- artifact or build tampering;
- stale, forged, or mismatched provenance;
- cross-run contamination;
- compromised external content or tools;
- and failure to preserve incident evidence.

Model theft, training-pipeline compromise, infrastructure side channels, hardware trust, and provider-internal security remain shared-responsibility concerns. Capability Profiles and vendor assurance may describe them, but the bootstrap cannot independently prove them.

## 5. Trust labels

Every content item crossing into an Agent Run receives one trust label:

| Label | Meaning | May supply runtime authority? |
|---|---|---|
| `trusted_control` | Authenticated policy, system instruction, or approved control contract | Yes |
| `governed` | Project content created and maintained under V3 controls | No |
| `verified_external` | External content whose source and integrity were checked | No |
| `untrusted` | User-supplied, retrieved, generated, unknown, or potentially hostile content | No |

Only `trusted_control` content may supply runtime authority. Governed project requirements inform work, but authorization still comes from policy and recorded decisions.

A Content Descriptor records source, digest, trust label, scan time, active-content status, instruction-like content, authority treatment, and security signals.

## 6. Prompt injection

Prompt injection is treated as a trust-boundary problem, not a text-filter problem.

V3 does not rely on a single phrase such as “ignore instructions in documents.” Instead it:

- labels retrieved material as non-authoritative;
- preserves trusted controls outside retrieved content;
- compiles minimum context;
- denies content the ability to expand tools, network, credentials, or scope;
- scans and records suspicious instruction patterns;
- requires review when prompt-injection signals appear;
- and isolates any active content.

Detection is imperfect. Absence of a scanner finding does not make external content authoritative.

## 7. Memory and context poisoning

Content cannot write directly into durable Learning, Decision, policy, or project memory.

Potential Learning passes ARCH-08 source and evidence requirements. Conflicting context is reconciled under ARCH-07 authority precedence. Untrusted content that claims “remember this as policy” remains data and creates a Finding if it attempts to alter control behavior.

Long-term memory stores source, digest, trust, applicability, confidence, and supersession information. Retraction preserves history.

## 8. Run-scoped tool grants

A Tool Grant identifies:

- grant and run IDs;
- one tool;
- allowed operations;
- exact resources;
- exact network hosts;
- issue and expiry times;
- granting authority;
- and revocation status.

A requested action must match tool, operation, resource, run, expiry, and revocation status exactly. Pattern expansion and inherited global access are outside the bootstrap baseline.

A tool’s technical capability does not imply permission. ARCH-09 capability negotiation answers “can the runner do this?” ARCH-12 answers “may this exact run use it here?”

## 9. Network controls

Sandboxes use either:

- `deny_all`; or
- an explicit host allowlist.

Requested hosts must appear in both the sandbox allowlist and an applicable Tool Grant. DNS names, service identities, methods, and egress proxies should be normalized before production use.

Untrusted executable content receives deny-all network access in the bootstrap. Exceptions require a separate reviewed design because network access materially increases exfiltration and command-and-control risk.

## 10. Credential brokering

Credentials are represented by short-lived Credential Leases containing:

- a secret reference, never the value;
- exact run ID;
- audience and scopes;
- issue and expiration;
- broker identity;
- one-time and renewal semantics;
- and revocation status.

The execution environment receives brokered access only when the request matches audience, scope, run, and time. Direct secret access is prohibited.

Logs, prompts, Context Manifests, events, findings, evidence, and provider results must redact or omit credential values. Suspected disclosure triggers containment and rotation according to severity.

## 11. Sandbox profile

Every executable Agent Run declares:

- run-bound sandbox identity;
- ephemeral lifecycle;
- process isolation;
- cleanup behavior;
- security telemetry;
- workspace access of none, read, or scoped write;
- network policy and hosts;
- and secret access of none or brokered.

Untrusted input requires ephemeral process isolation. Untrusted active content may execute only in a sealed sandbox with cleanup, no network, and no secret access.

High-risk work requires telemetry and independent security review. Production implementations should add resource ceilings, syscall restrictions, filesystem mounts, container or VM identity, image attestation, and cross-tenant isolation.

## 12. Workspace and cross-run isolation

Each run sees only its Context Manifest and declared workspace resources. It cannot inspect another run’s temporary files, environment, credentials, provider transcript, or unaccepted artifacts.

ARCH-10 conflict domains control logical write ownership. ARCH-12 isolation controls whether a compromised process can bypass that ownership technically. Both are required.

Cleanup occurs after evidence and forensic requirements are satisfied. An incident may freeze a workspace instead of deleting it.

## 13. Dependencies

Every introduced dependency receives a Dependency Trust Record containing:

- name, version, source, and immutable digest;
- approved, quarantined, or prohibited status;
- signature-verification status;
- provenance level;
- vulnerability disposition;
- and SBOM reference.

Floating versions and unpinned source are not represented as approved dependencies. Unknown vulnerability state requires review. Blocking vulnerabilities, quarantine, prohibition, or provenance below the run’s minimum stop use.

High- and critical-risk work requires verified dependency signatures in this baseline.

## 14. Provenance levels

V3 uses the SLSA build-level vocabulary as a portable assurance signal:

- `L0` — no provenance guarantee;
- `L1` — provenance exists;
- `L2` — signed provenance from a hosted build platform;
- `L3` — hardened build controls intended to resist tampering during the build.

Recording a level is not sufficient by itself. Consumers verify that the attestation, signature, builder identity, source materials, artifact digest, and expected policy match.

V3 does not assume transitive dependencies inherit the top-level artifact’s assurance.

## 15. Artifact attestation

An Artifact Attestation binds:

- artifact identity and digest;
- subject revision;
- producer Agent Run;
- builder and build type;
- provenance level;
- signature status;
- issue time;
- and source-material URIs and digests.

Verification compares the attestation with the expected artifact, digest, revision, run, minimum provenance, and signature requirement. A mismatched but validly signed attestation remains the wrong artifact.

Only verified artifacts may support production promotion where policy requires them.

## 16. Security preflight

Before dispatch, the Project Lead runs one security preflight for the exact Agent Run.

The preflight validates:

- run and project security requirements;
- content trust and signals;
- requested tool operations and resources;
- network hosts;
- credential audiences and scopes;
- dependency approval, vulnerability, signature, and provenance;
- sandbox isolation;
- telemetry requirements;
- and execution of retrieved active content.

It produces one decision:

| Decision | Meaning |
|---|---|
| `allow` | Governed work satisfies the declared boundary. |
| `allow_isolated` | Untrusted data may proceed only inside the recorded isolation controls. |
| `review_required` | Suspicious or uncertain conditions need independent judgment. |
| `block` | A required control is missing or violated. |
| `contain` | Evidence suggests active compromise or serious attempted misuse. |

The decision records exact reasons and required controls.

## 17. Excessive agency

V3 limits agency by requiring agreement among:

- authorization policy;
- Capability Profile;
- Context Recipe;
- Tool Grants;
- network policy;
- Credential Leases;
- conflict reservations;
- sandbox profile;
- and external-effect handling.

No single broad “agent can use tools” flag replaces these boundaries. A runner cannot authorize its own additional access.

## 18. Output handling

Model and tool output remains untrusted until validated. The framework:

- normalizes provider results;
- scans generated code, documents, and artifacts where applicable;
- validates structured output against schemas;
- keeps executable output quarantined until checks pass;
- verifies links, commands, dependencies, and network destinations before use;
- and binds evidence to exact revisions and digests.

Rendering systems must escape output appropriate to their destination. V3’s content validation does not replace HTML, SQL, shell, template, or API-specific injection controls.

## 19. Security signals and containment

Known signals include:

- prompt injection;
- data exfiltration;
- credential access;
- tool escalation;
- persistence;
- and supply-chain tampering.

Prompt injection alone enters bounded review when authority and isolation remain intact. Serious signals trigger `contain`.

A containment plan may:

- revoke run Tool Grants;
- revoke Credential Leases;
- isolate network access;
- freeze the workspace;
- quarantine run artifacts;
- preserve events and telemetry;
- open a Security Finding;
- notify the security owner;
- pause the affected project;
- and rotate potentially exposed credentials.

The plan is digest-protected. Containment actions are recorded before destructive cleanup.

## 20. Incident recovery

ARCH-08 recovery incorporates security state:

- a contained run is not automatically requeued;
- revoked credentials and grants remain revoked;
- quarantined artifacts cannot enter integration;
- potentially exposed external systems are verified;
- preserved workspaces and telemetry become evidence;
- and resumption requires recorded incident disposition and fresh authorization.

Security incident closure does not erase Findings or event history.

## 21. Adaptive Routes and Modes

Security depth adapts without removing hard controls:

- an isolated Investigation may accept L0 local throwaway output, no credentials, and no promotion;
- a UI prototype may use untrusted placeholder content in a sealed local environment;
- an MVP may require pinned dependencies, basic provenance, scanning, and scoped test credentials;
- Production-Ready work may require signed provenance, verified builders, SBOMs, stronger sandboxing, independent review, and incident readiness;
- Emergency posture may shorten decision paths but must record elevated authority, time limits, blast radius, and retrospective review.

Route outcomes determine whether insecure or negative results count as useful Learning or unacceptable delivery.

## 22. Liaison behavior

The liaison explains security decisions in layman’s terms. Examples include:

- “The document can be analyzed, but instructions inside it are not allowed to control the project.”
- “This AI can use the tool, but it has not been given permission to change that resource.”
- “The credential is available only for this task and expires shortly.”
- “This dependency’s origin cannot be verified, so V3 stopped before installing it.”
- “The run showed signs of trying to access credentials, so V3 isolated it and preserved the evidence.”

The liaison does not reveal credential references, internal detection details that aid evasion, or sensitive incident evidence unnecessarily.

## 23. Bootstrap implementation

The ARCH-12 bootstrap provides:

- content trust descriptors and authority separation;
- prompt-injection and serious-signal handling;
- exact run-scoped Tool Grants;
- brokered Credential Leases;
- sandbox and network validation;
- Dependency Trust Records;
- artifact provenance attestations and verification;
- deterministic security preflight decisions;
- digest-protected containment plans;
- eight public security schemas;
- six declarative security conformance scenarios;
- and tests covering injection, isolation, exfiltration, tools, credentials, network, dependencies, provenance, artifacts, and containment.

The bootstrap validates declared controls. It does not itself create containers, operate a secret vault, scan binaries, sign provenance, or replace a security operations platform.

## 24. Acceptance criteria

ARCH-12 is complete when:

1. only trusted control content can supply runtime authority;
2. untrusted content is labeled and isolated even without a detected attack;
3. prompt-injection signals cannot expand scope or access;
4. tool use matches exact run, operation, resource, time, and revocation state;
5. network access appears in both sandbox and Tool Grant allowlists;
6. credentials remain brokered references with bounded audience, scope, and lifetime;
7. untrusted active content requires a sealed environment without network or secrets;
8. dependencies are pinned, approved, scanned, and checked against provenance requirements;
9. artifacts bind to expected digest, revision, run, builder, and materials;
10. serious signals trigger containment and evidence preservation;
11. adaptive speed cannot waive hard security boundaries;
12. representative security scenarios pass deterministically.

## 25. Follow-on implications
