# V3.1-ARCH-10: Scheduler Conflict Domains and Cross-Workstream Integration

**Status:** Proposed architecture baseline  
**Version:** 0.1  
**Date:** 2026-09-17  
**Depends on:** V3.1-ARCH-02, V3.1-ARCH-06, V3.1-ARCH-08, and V3.1-ARCH-09

## 1. Purpose

This specification defines when V3-AIDLC may run work in parallel and how separately completed work becomes one verified result.

In plain terms, parallel agents are useful only when they do not trip over each other. V3 must know:

- what each job intends to read or change;
- which shared resources are already reserved;
- whether dependencies and source revisions are current;
- whether project, workstream, or runner capacity remains;
- which work should go first;
- and how completed pieces will be combined and tested together.

More agents do not automatically mean more speed. Coordination cost, conflicts, stale work, and integration failures may make sequential execution faster and safer.

## 2. Scheduler boundary

The Project Lead decides which eligible Work Packages become scheduling candidates. The scheduler does not invent work, waive dependencies, expand authorization, choose a different Mode, or accept results.

The scheduler produces a deterministic Schedule Plan from one canonical state revision. It selects safe candidates and explains every deferral. The State Kernel atomically converts selections into durable reservations and leases before dispatch.

If state changes before reservations are committed, the plan is stale and must be recalculated.

## 3. Schedule Candidate

Every candidate identifies:

- project, Work Package, and exact subject revision;
- Workstream, adapter, and role;
- priority class and user priority;
- queue time;
- unresolved dependency IDs;
- conflict-domain claims;
- and quota costs.

Eligibility under ARCH-02 remains a prerequisite. Scheduling does not turn an ineligible package into an eligible one.

## 4. Conflict domains

A conflict domain is a stable name for a resource whose concurrent use must be controlled. Examples include:

- `repo:file:src/catalog.py`
- `repo:tree:schemas`
- `database:schema:inventory`
- `deployment:environment:production`
- `external:airtable:base-123`
- `document:requirements-v4`
- `decision:pricing-model`

Each claim uses one access level:

| Access | Meaning | Compatible with |
|---|---|---|
| `read` | Observe without mutation | Other readers |
| `write` | Change the declared resource | No claim on the same domain |
| `exclusive` | Sole use is required even without mutation | No claim on the same domain |

The bootstrap compares exact domain identities. It does not infer that two paths overlap or that a child domain belongs to a parent. The planning layer must normalize claims at the correct shared granularity. This keeps conflict decisions explicit and auditable.

If the intended change surface is uncertain, the candidate uses a broader conservative domain or performs discovery before parallel implementation.

## 5. Reservations and leases

A Conflict and Quota Reservation records:

- reservation, project, Work Package, and subject-revision IDs;
- exact conflict claims;
- and consumed quota amounts.

Reservation and lease creation form one State Kernel transaction. V3 must not reserve capacity without a corresponding dispatchable lease, or lease work without reserving its declared conflict domains.

Release, expiration, and revocation are durable events. An expired lease does not make a resource safely reusable until ARCH-08 recovery reconciles the abandoned attempt and its possible effects.

## 6. Quotas

Scheduler Policy declares named concurrency limits. Dimensions may represent:

- all active project runs;
- one adapter or provider;
- one Workstream or role;
- one environment;
- scarce hardware;
- a cost or rate-limit pool;
- or a policy-defined operational boundary.

Each candidate declares non-negative costs for the dimensions it uses. Active reservations and earlier selections in the same plan consume capacity. Unknown dimensions fail closed instead of receiving unlimited capacity.

Quota values may vary by Route, Stage, Mode, Posture, risk, or operating condition. For example, Exploration Mode may permit several isolated experiments while a production deployment domain remains exclusive.

## 7. Candidate ordering

The bootstrap preserves the ARCH-02 order:

1. safety or recovery;
2. critical path;
3. user priority or deadline;
4. integration blocker;
5. intent value;
6. uncertainty reduction;
7. normal planned order.

Within the same effective class, higher user priority wins, followed by earlier queue time and stable Work Package ID.

Waiting work receives a bounded aging boost. Aging may improve ordinary work up to critical-path priority but cannot outrank mandatory safety and recovery. This prevents indefinite starvation without allowing old low-value work to suppress urgent controls.

## 8. Deterministic scheduling

For one canonical state revision, the scheduler:

1. validates the policy, candidates, and active reservations;
2. confirms the schedule concerns one project;
3. calculates active quota usage;
4. computes effective priority with bounded aging;
5. orders candidates deterministically;
6. checks dependencies and exact subject revisions;
7. compares claims with active and newly selected reservations;
8. checks every declared quota dimension;
9. selects safe candidates and tentatively reserves their claims and capacity;
10. records exact reasons for every deferral;
11. returns the Schedule Plan bound to the input state revision.

The same valid inputs produce the same plan.

## 9. Deferral reasons

Common deferrals include:

- dependency incomplete;
- current subject revision unknown;
- subject revision stale;
- conflict domain held by another Work Package;
- quota exceeded;
- or unknown quota dimension.

Deferral is not failure. The Project Lead records the reason and the wake condition: dependency completion, reservation release, refreshed revision, capacity change, or governed policy change.

## 10. Parallel dispatch transaction

Selections are proposals until the State Kernel commits them. For each selected candidate, the commit verifies that:

- the Schedule Plan still matches the current state revision;
- eligibility and authorization still hold;
- the Capability Profile still matches ARCH-09 negotiation;
- no conflicting reservation was committed concurrently;
- quota capacity still exists;
- and the subject revision remains current.

It then atomically records reservations, leases, Agent Run dispatches, and events. A partial batch is allowed only when policy explicitly permits it and the remaining plan is recalculated. Silent overbooking is never allowed.

## 11. Optimistic concurrency

The scheduler may calculate outside the State Kernel transaction, but commit uses optimistic concurrency against `stateRevision`.

If another actor changes a dependency, revision, reservation, quota, policy, or pause state first, the stale plan is rejected. The Project Lead reconciles and reschedules rather than forcing the old decision through.

## 12. Workstream independence

Separate Workstreams may execute concurrently when their declared dependencies and conflict domains permit it. Being in different Workstreams does not by itself prove independence.

Conversely, two packages in the same Workstream may run in parallel when their outputs are isolated, integration responsibility is assigned, and policy permits the coordination cost.

## 13. Integration groups

Every change intended to become part of a shared deliverable declares an integration group. Examples include a release candidate, prototype snapshot, schema migration set, or coordinated documentation revision.

An Integration Batch contains:

- one project and integration group;
- one exact target revision;
- one accountable integration owner role;
- required Checks;
- sorted member Work Packages;
- each member’s subject revision, artifact digest, and evidence;
- and a batch digest.

Only completed Agent Runs with evidence may enter a batch. Completion still means “ready for integration,” not “accepted into the product.”

## 14. Base revisions and stale work

Every member must declare the target revision on which its work was based. The bootstrap batch requires all members to match the exact target revision.

If the target moved, the member is stale. It must be rebased, regenerated, or independently verified against the new target before inclusion. V3 does not assume a clean textual merge means semantic compatibility.

## 15. Integration checks

Integration executes all Checks declared by the batch and applicable Gate policy. Depending on the work, these may include:

- build and test suites;
- schema compatibility;
- API or contract tests;
- migration and rollback tests;
- security and privacy checks;
- UI behavior and accessibility review;
- performance thresholds;
- artifact provenance;
- and independent semantic review.

An Integration Result is `passed`, `failed`, or `inconclusive`. A passed result requires every declared Check to pass, accepted evidence, and a new resulting revision. Failed or inconclusive integration cannot claim a promoted revision.

## 16. Integration failure

Integration failure creates Findings against the combined batch and, where evidence permits, affected members. The Project Lead classifies whether the cause is:

- a member defect;
- incompatible assumptions between members;
- a stale base revision;
- an integration-environment problem;
- a test or oracle defect;
- or a framework scheduling defect.

Repair may target one member, several members, the integration plan, or the scheduler itself. Independently completed members are not erased from history, but they remain unaccepted for the shared target.

## 17. Promotion and rollback

Only a passed Integration Result may supply evidence to an integration, promotion, or release Gate. Passing integration does not automatically authorize deployment or another external effect.

If a promoted integration later fails, rollback follows the governed release and recovery policy. The framework preserves the failed resulting revision, evidence, and Finding rather than rewriting the batch as though it never passed.

## 18. Adaptive speed

This model supports different development speeds without creating separate SDLCs:

- an Investigation may parallelize isolated trials and integrate only their Learning;
- a UI prototype may parallelize independent screens against a fixed design contract;
- an MVP may use moderate quotas and a focused integration suite;
- Production-Ready work may use narrower conflict domains only when ownership is precise, stronger independent checks, and exclusive deployment reservations.

The active Route and Modes tune quotas and required integration checks. They do not remove revision, conflict, or evidence controls.

## 19. Recovery

After interruption, ARCH-08 reconstructs reservations, leases, dispatches, and integration state from verified history.

- Live leases retain their reservations.
- Expired attempts are reconciled before release and retry.
- Completed members without a durable batch remain ready for integration.
- A batch with an uncertain external effect is verified before repetition.
- A stale Schedule Plan is discarded and recalculated.

Conversation history is not used to guess which resources remain reserved.

## 20. Liaison behavior

The liaison explains scheduling in layman’s terms. Examples include:

- “These two jobs can run together because they touch different parts of the project.”
- “This job is waiting because another agent is changing the same database structure.”
- “The pieces finished separately, but they still need to be combined and tested together.”
- “The source changed while this agent was working, so its result must be refreshed before integration.”
- “Adding another agent would not make this step faster because the shared environment allows only one safe writer.”

The liaison does not equate queueing with failure or imply that individually completed work has passed integration.

## 21. Bootstrap implementation

The bootstrap provides:

- exact read, write, and exclusive conflict claims;
- active and tentative reservation checks;
- named quota limits and consumption;
- dependency and subject-revision validation;
- deterministic priority and bounded aging;
- stable selected and deferred Schedule Plans;
- revision-bound Integration Batches;
- tamper-evident batch digests;
- strict Integration Result validation;
- JSON Schemas for policy, candidates, reservations, plans, batches, and results;
- and tests covering concurrency, quotas, fairness, stale work, batch integrity, and integration evidence.

## 22. Acceptance criteria

ARCH-10 is complete when:

1. parallel work declares explicit conflict-domain claims;
2. readers may share while writes and exclusive claims prevent unsafe overlap;
3. active and same-plan reservations both consume conflict and quota capacity;
4. incomplete dependencies and stale or unknown revisions defer dispatch;
5. unknown quota dimensions fail closed;
6. ordering is deterministic and bounded aging prevents starvation;
7. selections remain proposals until atomically committed against the same state revision;
8. separately completed work enters one revision-bound Integration Batch;
9. batch content is digest-protected and stably ordered;
10. passed integration requires every declared Check, evidence, and a new revision;
11. failed or inconclusive integration cannot claim promotion;
12. representative scheduling and integration scenarios pass deterministically.

## 23. Follow-on implications

ARCH-11 should assemble the architecture contracts into a reference orchestrator and exercise end-to-end conformance scenarios across liaison intake, planning, authorization, context, scheduling, dispatch, evidence, integration, and recovery.
