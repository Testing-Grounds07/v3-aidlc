# V3.1-ARCH-13: Observability, SLOs, Cost Accounting, and Deployment Topology

**Status:** Proposed architecture baseline  
**Version:** 0.1  
**Date:** 2026-09-17  
**Depends on:** V3.1-ARCH-08, V3.1-ARCH-10, V3.1-ARCH-11, and V3.1-ARCH-12

## 1. Purpose

This specification defines how V3-AIDLC is operated, measured, paid for, recovered, changed, and judged ready for production.

In plain terms, a system is not production-ready merely because its features work once. Its operators must be able to tell what it is doing, notice trouble, control spending, restore lost service, change stored data safely, and explain whether deployment is safe. ARCH-13 makes those expectations explicit and testable.

## 2. Research basis

The baseline draws on:

- the [Google SRE guidance on service-level objectives](https://sre.google/sre-book/service-level-objectives/) for measuring the reliability users experience and using error budgets to balance reliability with change;
- the [OpenTelemetry signal model](https://opentelemetry.io/docs/concepts/signals/) for portable traces, metrics, and logs, supplemented in V3 by governed audit events;
- the [FinOps Open Cost and Usage Specification](https://focus.finops.org/) for normalized, attributable cost and usage data;
- and [NIST SP 800-34 Rev. 1](https://csrc.nist.gov/pubs/sp/800/34/r1/upd1/final) for contingency planning, recovery objectives, and tested restoration.

These sources provide operating patterns. V3's schemas, policies, and executable evaluators remain the governing implementation contracts.

## 3. Operating principles

V3 follows these rules:

1. **Measure user-visible outcomes.** Internal activity is useful, but success, latency, durability, and recovery are what determine service health.
2. **Correlate without oversharing.** Operational records carry stable IDs, not raw prompts, responses, credentials, or unrestricted content.
3. **Treat cost as a governed resource.** Usage is attributed to the project, work package, run, provider, and model before it is aggregated.
4. **Prove recovery.** A backup is not considered dependable until its integrity and restoration have been tested.
5. **Change data in reversible steps.** Schema and state migrations expand, backfill, verify, switch, and only then remove old structures.
6. **Require evidence for readiness.** Production promotion depends on current control results, not confidence or a checklist marked by assertion.
7. **Adapt the weight, not the safety boundary.** A local experiment can use lighter operations than a production service, but it cannot misrepresent its readiness.

## 4. Deployment topology

The logical production topology contains:

| Component | Responsibility |
|---|---|
| Liaison or gateway | Speaks with the user in layman's terms and translates requests and status. |
| Project Lead | Chooses Routes, plans work, enforces policy, and coordinates decisions. |
| Scheduler and workers | Reserve conflict domains and execute bounded Agent Runs. |
| Provider and tool adapters | Normalize external capabilities and results. |
| State service | Owns authoritative project state and event ordering. |
| Artifact and evidence store | Keeps immutable outputs, attestations, and verification evidence. |
| Credential broker | Issues narrow, short-lived credential leases without exposing secret values. |
| Telemetry pipeline | Receives, redacts, retains, and presents operational signals. |

There must be exactly one **logical** authority for project state. It may be implemented with replicated infrastructure, but clients cannot independently declare competing state histories authoritative. Stateless liaison, orchestration, adapter, and worker processes may scale horizontally when their work is tied to the same authoritative state and idempotency controls.

Connections that carry governed data must be encrypted. Identity, authorization, and isolation follow ARCH-12.

## 5. Environment separation

Development, test, staging, and production environments have separate identities, credentials, state, evidence, and deployment permissions. Test data cannot silently become production state. Production access is narrower and more strongly audited than lower environments.

Promotion moves an identified, attested artifact through environments; it does not rebuild an untracked substitute. Configuration may differ, but the artifact identity remains verifiable.

## 6. Operational signals

V3 recognizes four signal kinds:

| Signal | Plain-language use |
|---|---|
| Trace | Follows one request or run across components. |
| Metric | Shows a numerical trend such as success rate, latency, queue depth, or cost. |
| Log | Records a diagnostic event for investigation. |
| Audit | Records a security- or governance-relevant action and its actor. |

Each record includes record, trace, and project IDs; a timestamp with timezone; signal name; sensitivity; redaction status; and scalar attributes. Trace records also include a span ID. Work-package, run, route, stage, mode, gate, and artifact IDs are added when applicable.

Telemetry must not contain raw prompts, raw responses, unrestricted content, secrets, tokens, credentials, authorization headers, or cookies. Sensitive detail belongs in access-controlled evidence where retention and disclosure are explicit. Attribute values should use bounded vocabularies so a unique value for every event does not make telemetry unusably expensive.

## 7. Service indicators and objectives

A service-level indicator, or SLI, is a measurement. A service-level objective, or SLO, is the target for that measurement over a stated window.

V3 supports these baseline indicators:

- availability;
- successful outcomes;
- latency;
- durability of accepted state or artifacts;
- and recovery time.

Every SLO names a service, measurement kind, target, evaluation window, and minimum sample count. Ratio targets range from zero to one. Latency and recovery targets use a stated percentile so a good average cannot hide severely slow requests.

Insufficient samples produce no reliability claim. Implementations should report the missing evidence rather than treating an empty period as perfect service.

## 8. Error budgets

For a ratio SLO, the error budget is the allowed gap from perfection. For example, a 99.9% success objective allows 0.1% unsuccessful outcomes during its window.

When the budget is healthy, normal change may continue. As it is consumed, the Project Lead may require smaller deployments, more review, or remediation. When exhausted, production-changing work is blocked unless an authorized human accepts a documented exception. Error budgets guide change velocity; they do not excuse security, privacy, or integrity violations.

## 9. AI-specific health indicators

AI-enabled work also records indicators such as:

- structured-output validation rate;
- Check and Gate pass rate;
- retry and recovery rate;
- invalid-context or capability-negotiation rate;
- human correction or escalation rate;
- and provider refusal, timeout, or malformed-result rate.

These indicate whether the delivery machinery behaves reliably. They are not, by themselves, proof that a product is correct, useful, fair, or safe. Product claims still need domain-appropriate evaluation and evidence.

## 10. Usage and cost ledger

Each usage entry is immutable and identifies the project, work package, Agent Run, provider, model, occurrence time, and currency. It records non-negative integer quantities for input units, output units, tool seconds, storage byte-hours, and cost in millionths of the currency unit.

Integer micro-units avoid floating-point rounding errors. Aggregation rejects duplicate entry IDs and mixed currencies. Conversion, discounts, shared infrastructure allocation, taxes, and provider reconciliation are separate, explicit processes rather than hidden arithmetic.

## 11. Budgets

A budget defines a dimension, period, warning threshold, and hard limit. Evaluation returns:

| Decision | Meaning |
|---|---|
| `within` | Normal work may continue. |
| `warn` | Continue visibly and consider a cheaper plan. |
| `block` | Stop new discretionary consumption and ask for an authorized decision. |

Budgets may apply to money, model units, tool time, storage, or another governed measure. Raising a limit is a recorded decision; the system cannot silently expand its own allowance.

## 12. Capacity, queues, and backpressure

Schedulers enforce per-project and per-provider concurrency, rate, and cost limits. Queue depth, wait time, saturation, and rejection rate are measured. When capacity is unavailable, V3 queues bounded work, selects an approved alternative, reduces optional work, or reports the constraint. It does not create uncontrolled retries.

Priority affects ordering, not authorization. Emergency work cannot take another workstream's conflict domain or exceed a hard budget without the same governed exception required elsewhere.

## 13. Backup and restoration

Every governed dataset has a backup policy naming:

- recovery point objective (RPO): how much recent data may be lost;
- recovery time objective (RTO): how long restoration may take;
- encryption and retention requirements;
- integrity verification;
- and restore-test frequency.

Authoritative state, artifacts, evidence, policy/configuration, and essential audit history may have different targets. A restore observation passes only when the backup is recent enough, restoration is fast enough, encryption and integrity checks pass, and an actual restore test succeeds.

Snapshots do not replace the authoritative event and state model. Restoration preserves identity and provenance or explicitly records their reconstruction.

## 14. State and schema migrations

Migrations follow five ordered phases:

1. `expand` — add compatible structures;
2. `backfill` — populate them without removing the old path;
3. `verify` — prove equivalence and integrity;
4. `switch` — move authoritative reads and writes;
5. `contract` — remove the obsolete structure after rollback risk is accepted.

Completed phases must be contiguous and have evidence. Before the switch, the migration remains backward compatible. Every migration declares a rollback procedure. Destructive contraction waits for retention, backup, and rollback policy.

## 15. Availability and failure domains

Production design identifies failure domains for compute, state, storage, identity, credentials, external providers, and telemetry. Replication and failover are chosen from the service objectives rather than assumed universally.

The system degrades explicitly. If optional analytics fail, core state may continue. If authoritative state, identity, or required security controls are unavailable, unsafe mutations stop. Health checks distinguish process availability from dependency and end-to-end readiness.

## 16. Deployment, release, and rollback

Each release names the artifact digest, source revision, attestation, configuration version, migration state, target environment, approvals, and rollback plan. Checks run against the exact candidate.

Production Routes may use staged rollout, canaries, feature controls, or parallel verification where appropriate. Promotion pauses or reverses when SLO, security, migration, or business guardrails fail. A rollback is itself a governed change with evidence; it is not assumed safe merely because it points to an older version.

## 17. Production-readiness decision

Readiness evaluates required controls and their evidence. Baseline production controls include:

- current functional and end-to-end Checks;
- security preflight and artifact provenance;
- declared SLOs and telemetry coverage;
- usage attribution and applicable budgets;
- tested backup and restoration;
- migration and rollback readiness;
- topology and environment separation;
- on-call ownership and incident path;
- and privacy, retention, and compliance obligations.

The result is `ready`, `not_ready`, or `inconclusive`. A failed control makes the candidate not ready. Missing evidence makes it inconclusive. Neither condition may be rewritten as ready by optimism; exceptions require an authorized, time-bounded decision with known consequences.

## 18. Incidents and user communication

Operational alerts create Findings under ARCH-08 and preserve correlation, affected scope, evidence, and containment actions. Incident roles, severity, escalation, communication interval, and recovery authority are defined before production use.

The liaison explains incidents in layman's terms: what users are experiencing, what is affected, what is safe to do, what the team is doing, and when the next useful update is expected. Technical identifiers remain available for operators, but the user is not required to decode internal terminology.

## 19. Adaptive application by Mode and Route

Operational depth follows the work's actual exposure:

| Work posture | Typical operational requirement |
|---|---|
| Local trial or disposable experiment | Basic run correlation, resource ceiling, no production data, and explicit non-production label. |
| MVP or limited pilot | Usage attribution, basic health measures, bounded users/data, backup where state matters, and a shutdown path. |
| High-resolution interface work | Preview reliability, artifact/version traceability, privacy-safe analytics, and accessibility evidence. |
| Production-bound work | Full readiness controls, SLOs, budgets, recovery tests, migrations, provenance, incident ownership, and rollback. |

A project may operate several workstreams at different postures. Each workstream declares its posture and inherited Route. Shared production components satisfy the strongest applicable controls. Moving toward production adds evidence and controls; relabeling work does not erase its real risk.

## 20. Privacy, retention, and deletion

Telemetry, usage, backups, and incident evidence have explicit owners, sensitivity, access policy, retention period, and deletion or legal-hold behavior. Identifiers are minimized or pseudonymized where practical. Deleting primary data also accounts for backups and derived records according to documented retention constraints.

Audit evidence remains sufficient to explain important actions without storing prohibited prompt, response, or secret content.

## 21. Bootstrap implementation

The bootstrap supplies:

- JSON Schemas for telemetry, SLOs, usage, budgets, backups, migrations, topology, and readiness;
- executable validation and evaluation in `src/v3_aidlc/operations.py`;
- and six conformance scenarios covering redaction, error budgets, usage attribution, recovery targets, reversible migrations, and readiness.

The bootstrap does not deploy databases, collectors, dashboards, billing integrations, failover infrastructure, backup services, or an on-call platform. Production implementations bind the contracts to concrete infrastructure and test that binding.

## 22. Acceptance criteria

ARCH-13 is satisfied when:

1. operational records are correlated, redacted, typed, and schema-valid;
2. SLO evaluation rejects insufficient or invalid evidence and calculates the declared objective consistently;
3. usage is exactly attributable and aggregation rejects duplicates and mixed currencies;
4. budget evaluation produces deterministic within, warn, or block decisions;
5. recovery evidence tests RPO, RTO, encryption, integrity, and restoration;
6. migrations preserve the required order, compatibility, evidence, and rollback path;
7. topology has one logical state authority and encrypted governed connections;
8. readiness cannot pass with failed controls or missing evidence;
9. operating expectations adapt to the work posture without weakening hard security or integrity boundaries;
10. and user-facing operational communication uses clear, non-technical language.
