# V3.1-ARCH-11: Reference Orchestrator and End-to-End Conformance

**Status:** Proposed architecture baseline  
**Version:** 0.1  
**Date:** 2026-09-17  
**Depends on:** V3.1-ARCH-01 through V3.1-ARCH-10

## 1. Purpose

This specification assembles the preceding architecture contracts into one executable reference Project Lead and defines end-to-end conformance scenarios.

In plain terms, the earlier packages defined the parts. ARCH-11 proves that the parts can work together in the intended order.

The reference orchestrator demonstrates that V3 can:

- recognize when ordinary conversation should become managed project work;
- select the correct Route, Stage, Modes, and Posture;
- stop before execution when authority is missing;
- assemble only the context needed for one bounded job;
- select a capable AI runner without assuming provider abilities;
- schedule safe parallel work;
- bind dispatch to an exact context, capability profile, lease, and revision;
- normalize runner output;
- require evidence and Gates before acceptance;
- integrate parallel results against one revision;
- produce a durable, verifiable trace;
- and recover interrupted work without relying on the prior chat.

## 2. Reference, not production

The bootstrap reference orchestrator is an executable architecture proof. It is deliberately deterministic and synchronous.

It is not yet:

- a network service;
- a production job queue;
- a distributed transaction coordinator;
- a live AI-provider integration;
- a user interface;
- or a replacement for the canonical State Kernel transaction boundary.

This distinction prevents a passing simulation from being described as a deployable production control plane.

## 3. Runtime assembly

The reference runtime connects the packages in this order:

1. **Gateway activation** — determine whether the request stays conversational or attaches to managed work.
2. **Lifecycle selection** — validate the Route and select Stage Modes and Posture.
3. **Authorization** — evaluate each proposed action against all applicable policies.
4. **Context compilation** — create a minimum, provenance-preserving Context Manifest.
5. **Capability negotiation** — choose a runner whose current profile satisfies the exact Agent Run Request.
6. **Scheduling** — check dependencies, revisions, conflict domains, priorities, and quotas.
7. **Dispatch** — pin the request, profile, context, lease, attempt, and digests.
8. **Result normalization** — translate provider output into the V3 result contract.
9. **Evidence and Gate evaluation** — decide whether the result is admissible and promotable.
10. **Integration** — combine accepted parallel members against one target revision and run combined checks.
11. **Durable trace** — append hash-linked events and produce a plain-language outcome.
12. **Recovery** — reconcile expired or uncertain work before any retry.

No later phase repairs an omitted earlier control. For example, a passing test cannot retroactively authorize an unapproved dispatch.

## 4. Input boundary

A conformance execution receives already resolved governed contracts and bounded work declarations. These include:

- project and scenario identities;
- canonical state revision and current time;
- activation facts;
- Route, Mode library, Stage, Posture, and authoritative route facts;
- authorization policies;
- Context Recipe;
- proposed Work Packages;
- active reservations and scheduler policy;
- completed dependencies and current subject revisions;
- registered adapters;
- acceptance Gate inputs;
- and optional integration instructions.

The reference runtime does not fetch hidden context or silently repair incomplete inputs. Invalid scenario structure raises a conformance error. Governed negative outcomes such as missing permission, capability mismatch, failed Gates, or conflict deferral produce a trace rather than disappearing as exceptions.

## 5. Adapter registry

The runtime accepts adapters through the ARCH-09 interface. Adapter IDs must be unique. Each adapter publishes its current Capability Profile and handles only dispatches selected for that exact adapter.

Conformance tests use deterministic fake adapters. This proves orchestration behavior without requiring vendor credentials, consuming model capacity, or confusing provider behavior with framework correctness.

Live adapters remain subject to the same profile, dispatch, result, evidence, and recovery contracts.

## 6. Work preparation

For every proposed Work Package, the runtime:

1. evaluates authorization;
2. records the controlling decision;
3. stops that package if blocked or awaiting the user;
4. compiles context for authorized work;
5. fills the Agent Run Request with the exact Context Manifest identity and size;
6. negotiates all registered Capability Profiles;
7. records a selected adapter or exact rejection reason;
8. and admits only prepared work to scheduling.

This ensures permission failure occurs before context disclosure and execution.

## 7. Scheduling and dispatch

Prepared packages enter the ARCH-10 scheduler. Deferred work retains explicit reasons and is reported as waiting rather than failed.

For each selected package, the reference runtime creates a lease-bound dispatch and invokes the selected adapter. The simulation executes selected work in stable order, while the Schedule Plan proves which work is safe to run concurrently in a real runtime.

Production implementations may execute the selected batch concurrently only after atomic reservation and lease commit.

## 8. Results and acceptance

Adapter output is normalized before evaluation. The trace never stores an opaque provider response.

A runner reporting completion without an acceptance Gate is not accepted. Completed output must pass its configured Gate using revision-bound, admissible evidence. Failed, blocked, cancelled, or non-promotable work makes the scenario fail or wait according to its governed state.

This distinction remains central:

> The AI saying “done” is an execution claim. V3 acceptance requires evidence.

## 9. Integration

When a scenario requires combined delivery, every expected member must:

- have been selected and completed;
- pass its package Gate;
- provide evidence;
- declare the same project, integration group, and target base revision;
- and supply a stable artifact digest.

The orchestrator builds one digest-protected Integration Batch and validates its Integration Result. A missing member blocks the batch. Failed or inconclusive combined checks prevent completion.

## 10. Durable trace

Every managed execution produces an Orchestration Trace containing:

- scenario, project, route, Stage, Modes, and state revision;
- overall status and plain-language summary;
- per-package authorization, context, adapter, scheduling, run, Gate, and reason fields;
- the Schedule Plan;
- optional Integration Batch and outcome;
- and hash-linked canonical-style events.

Trace validation verifies:

- known status;
- required identities;
- unique Work Package entries;
- a valid event chain for managed work;
- one project boundary;
- agreement between selected schedule entries and Work Package traces;
- and the presence of a batch whenever integration claims to pass.

An unmanaged conversational trace contains no managed execution events, Schedule Plan, or Integration Batch.

## 11. Trace status

| Status | Meaning |
|---|---|
| `not_managed` | The request remains an ordinary conversation. |
| `completed` | Selected work and all required package and integration checks passed. |
| `waiting` | Safe work may have run, but at least one package remains queued. |
| `decision_required` | A material action requires user judgment or authority. |
| `blocked` | A hard control, missing permission, context failure, or capability gap prevents progress. |
| `failed` | Execution, verification, or integration produced an unacceptable result. |

Overall status does not erase individual Work Package outcomes. A production runtime may support mixed progress across larger plans while preserving this same per-package trace.

## 12. Conformance catalog

The bootstrap catalog declares seven foundational scenarios:

| ID | Scenario | Expected outcome |
|---|---|---|
| `CONF-01` | Routine bounded work completes | `completed` |
| `CONF-02` | Missing permission blocks dispatch | `blocked` |
| `CONF-03` | Material external action returns to the user | `decision_required` |
| `CONF-04` | Parallel changes integrate together | `completed` |
| `CONF-05` | Conflicting changes wait safely | `waiting` |
| `CONF-06` | Interrupted reversible work is requeued | recovery action |
| `CONF-07` | Uncertain external effect is checked first | recovery action |

Executable tests also cover capability mismatch, failed Gates, trace serialization, event-chain integrity, and trace tampering.

## 13. Happy-path conformance

The routine managed scenario proves this chain:

1. an existing project reference activates the Project Lead;
2. the Production-Ready Route selects Architecture and Independent Review for Design;
3. local reversible work receives standing authorization;
4. required objective, requirement, constraint, and tool context is compiled;
5. a capable deterministic adapter is selected;
6. the candidate passes revision, conflict, dependency, and quota checks;
7. dispatch pins the request and context;
8. normalized completion identifies artifacts, evidence, and satisfied criteria;
9. the automated-test Check is admissible for the exact revision;
10. the package Gate passes;
11. the event chain verifies;
12. and the runtime reports completion in plain language.

## 14. Authorization conformance

The missing-permission scenario proves that blocked work receives no Context Manifest and no dispatch.

The irreversible-external-action scenario proves that the Project Lead returns the action for user decision rather than allowing the liaison, scheduler, adapter, or evidence system to authorize it indirectly.

## 15. Capability conformance

The mismatch scenario uses an adapter that can edit code but cannot execute required tests. Negotiation fails before scheduling and records the missing capability.

The runtime does not weaken the completion criteria, omit the test requirement, or infer support from the adapter’s name.

## 16. Parallel-work conformance

The independent-work scenario selects two packages with separate conflict domains. Both complete and pass package Gates, then enter one target-revision-bound Integration Batch whose combined check passes.

The conflict scenario gives two writers the same database domain. One is selected deterministically and the other waits with the holding Work Package identified. The deferred work is neither duplicated nor mislabeled as failed.

## 17. Evidence conformance

The failed-Gate scenario uses an otherwise successful Agent Run with a failed required Check. The scenario status is failed even though the adapter reported completion.

This proves that orchestration preserves the separation between execution and acceptance.

## 18. Recovery conformance

The reversible interruption scenario presents an expired active lease for local work within its attempt budget. Recovery selects `reclaim_and_requeue`.

The external-effect scenario presents an expired attempt that may have performed a consequential action. Recovery selects `verify_external_effect`, not automatic retry.

Both scenarios reconstruct from verified events and leases rather than conversation memory.

## 19. Main-chat liaison

When the user interacts through a normal AI chat instead of invoking V3 directly, the liaison remains outside this runtime boundary.

The liaison:

- recognizes or asks whether the work belongs to a managed project;
- relays the user’s request without rewriting its meaning;
- receives the Project Lead’s trace or decision request;
- explains the result in layman’s terms;
- and returns corrections, decisions, delegations, or revocations through ARCH-05.

It does not directly modify canonical state, invent completion, or expose raw internal trace details that do not help the user.

## 20. Conformance levels

Future implementations may declare:

- **contract conformance** — public schemas and validation behavior match;
- **scenario conformance** — required catalog scenarios produce expected outcomes;
- **recovery conformance** — interruption and external-effect behavior match;
- **operational conformance** — durable transactions, isolation, security, observability, and load behavior meet production requirements.

Passing the bootstrap tests demonstrates the first three at reference scale. It does not yet demonstrate operational conformance.

## 21. Extension rules

New adapters, Modes, Routes, policies, Checks, Gates, scheduler dimensions, or recovery actions may extend the runtime when they:

- preserve existing versioned contract meanings;
- add explicit capability and authorization requirements;
- provide deterministic conformance scenarios;
- retain exact subject and context identities;
- and fail closed when an extension is unknown.

Provider-specific shortcuts cannot bypass the reference sequence.

## 22. Bootstrap implementation

The ARCH-11 bootstrap provides:

- an executable `ReferenceOrchestrator`;
- deterministic adapter registration and invocation;
- complete managed and unmanaged trace construction;
- policy, context, capability, scheduler, dispatch, Gate, integration, event, and recovery composition;
- trace serialization and self-validation;
- Orchestration Trace and conformance schemas;
- a seven-scenario catalog;
- and executable tests for successful, waiting, blocked, decision, failed, integrated, and recovery outcomes.

## 23. Acceptance criteria

ARCH-11 is complete when:

1. ordinary conversation can remain outside managed execution;
2. one reference runtime composes ARCH-01 through ARCH-10 in the required order;
3. permission failure prevents context disclosure and dispatch;
4. capability failure prevents scheduling without weakening requirements;
5. safe parallel work produces one verified Integration Batch;
6. conflicting work is deferred with an exact reason;
7. runner completion cannot bypass evidence Gates;
8. traces bind work decisions to a valid event chain and Schedule Plan;
9. recovery differentiates reversible work from uncertain external effects;
10. user-facing summaries remain plain-language outcomes;
11. schemas, catalog, and tests validate;
12. and limitations of the reference runtime are explicit.

## 24. Follow-on implications

ARCH-12 should define the AI-specific security boundary: untrusted-input handling, prompt-injection resistance, tool and workspace isolation, credential brokering, artifact provenance, dependency and model supply-chain controls, and incident containment.
