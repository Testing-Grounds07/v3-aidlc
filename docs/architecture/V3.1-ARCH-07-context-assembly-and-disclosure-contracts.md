# V3.1-ARCH-07: Context Assembly and Disclosure Contracts

**Status:** Proposed architecture baseline  
**Version:** 0.1  
**Date:** 2026-09-16  
**Depends on:** V3.1-ARCH-01 through V3.1-ARCH-06

## 1. Purpose

This specification defines how V3-AIDLC builds the context given to an agent or tool.

In plain terms, an agent should receive enough trustworthy information to do its assigned job, but not the entire project, unrelated conversations, unnecessary sensitive data, hidden credentials, or another agent’s private scratch work.

Every Agent Run receives a compiled, versioned Context Manifest. The manifest identifies what was included, where it came from, what was excluded, which tools and network destinations are allowed, and a digest that detects changes.

## 2. Governing principles

1. **Minimum necessary context.** Inclusion requires scope and task relevance, not possible usefulness.
2. **Provenance before convenience.** Every item identifies its source and integrity.
3. **Authority is explicit.** Summaries and assumptions cannot override policies, user instructions, canonical state, or governed contracts.
4. **Sensitive disclosure is exact.** Broad role access is insufficient for confidential, restricted, or secret material.
5. **Secrets remain references.** Raw secret values never enter stored context items or manifests.
6. **Conflicts fail closed.** Equally authoritative contradictory facts require reconciliation.
7. **Roles receive different views.** An implementer and independent reviewer should not automatically receive the same context.
8. **Tools are context.** Filesystem, network, and tool access are allowlisted alongside information.
9. **Private reasoning is not project data.** Hidden chain-of-thought and model scratch work are neither persisted nor redistributed.
10. **Compilation is reproducible.** Identical governed inputs produce the same manifest digest.

## 3. Context Items

A Context Item is a bounded, attributable unit such as:

- instruction;
- objective;
- requirement;
- constraint;
- decision;
- architecture statement;
- artifact or evidence reference;
- finding or learning;
- approved conversation excerpt;
- tool contract;
- secret reference;
- external fact;
- or explicitly labeled assumption.

Each item records a stable ID and revision, source type and source reference, sensitivity, integrity, project and entity scope, applicable Stages, Modes, and roles, relevance tags, creation and optional expiration times, a claim key, and whether it must always be included within its authorized scope.

## 4. Source types and precedence

The bootstrap precedence order is:

| Source | Rank | Meaning |
|---|---:|---|
| Organization policy | 100 | Non-project rules and mandatory boundaries |
| Project policy | 95 | Project-specific governed rules |
| User instruction | 90 | Verbatim or recorded user direction |
| Canonical state | 85 | Current accepted project facts |
| Governed contract | 80 | Route, Mode, Check, Gate, role, or protocol contract |
| Verified evidence | 70 | Admissible evidence accepted under ARCH-06 |
| External source | 40 | Attributed information not yet made canonical |
| Liaison summary | 20 | Helpful translation that is not authoritative state |
| Assumption | 10 | Explicitly provisional working belief |

Precedence is applied only among items sharing a claim key. A higher-ranked source wins and the excluded item remains listed in the manifest explanation.

If equally ranked active items make different claims, compilation stops. The Project Lead must reconcile the conflict rather than allowing ordering, recency, or model preference to choose silently.

External sources and liaison summaries cannot label themselves authoritative. Assumptions must use both assumption source and assumption integrity.

## 5. Scope and relevance

An item is eligible only when:

- its project matches the Agent Run;
- any declared entity scope intersects the run’s entity lineage;
- any declared Stage, Mode, and role restrictions match;
- it is not expired;
- its kind and source are allowed by the role’s Context Recipe;
- its sensitivity does not exceed the recipe maximum;
- required disclosure authority exists;
- and it is either marked always-include or shares a bounded task tag with the run.

Every run must declare at least one task tag. An empty relevance scope cannot be used to collect all otherwise eligible project data.

## 6. Sensitivity

The levels are:

- `public`
- `internal`
- `confidential`
- `restricted`
- `secret`

Public and internal items may be selected when the recipe permits them. Confidential, restricted, and secret items require an exact Disclosure Grant in addition to recipe permission.

Sensitivity is independent of authority. A highly authoritative item may still be unavailable to a particular agent.

## 7. Disclosure Grants

A Disclosure Grant names:

- exact project;
- recipient role;
- exact Agent Run IDs;
- exact Context Item IDs;
- stated purpose;
- accountable grantor;
- accepted authority source;
- and expiration time.

Accepted grant authorities are organization policy, project policy, or a recorded user decision. A matching role alone does not grant access. A grant for another run, project, item, or expired period does not disclose the material.

Disclosure does not expand tool permissions or authorize the agent to use information for another purpose. Those remain separately governed.

## 8. Secret handling

Raw secrets must never be stored in Context Items, Context Manifests, prompts, logs, evidence, or conversation summaries.

A secret is represented by a `secret_reference` containing an opaque reference, such as a secret-manager locator. It must use secret sensitivity and requires an exact Disclosure Grant. The execution environment resolves the reference only at the authorized tool boundary and should avoid exposing the value to the model whenever possible.

If a raw secret is supplied as ordinary content, validation fails rather than redacting it after persistence.

## 9. Context Recipes

A versioned Context Recipe defines one role’s context boundary:

- allowed and required item kinds;
- allowed source types;
- maximum sensitivity;
- item and byte budgets;
- deterministic kind priority;
- tool allowlist;
- and network allowlist.

The bootstrap includes separate recipes for implementation and independent review.

The implementation recipe permits bounded findings, learning, and secret references because an authorized repair or integration may need them. It permits write tools but no network by default.

The independent-review recipe is read-only, excludes liaison summaries and assumptions, excludes implementation findings that could anchor the reviewer to the implementer’s framing, requires artifact and evidence references, and allows confidential information only with an exact grant.

## 10. Context compilation

The compiler:

1. validates the Context Recipe, Agent Run, Context Items, and Disclosure Grants;
2. filters by kind, source, sensitivity, project, scope, expiry, grant, and task relevance;
3. groups competing statements by claim key;
4. applies source precedence;
5. stops on equal-authority contradictions;
6. sorts remaining items by mandatory status, authority, recipe kind priority, and stable ID;
7. applies maximum item and byte budgets;
8. verifies every required kind remains present;
9. emits selected items and exclusion reasons;
10. binds tool and network allowlists;
11. creates a canonical digest and manifest ID.

If a budget would remove a required kind, compilation fails. The compiler does not silently create an under-informed Agent Run.

## 11. Context Manifest

The manifest records:

- manifest and run IDs;
- role and exact recipe version;
- generation time;
- selected item IDs, revisions, values or permitted references;
- source, sensitivity, integrity, and claim key for each item;
- exclusions and reasons;
- tool and network allowlists;
- total compiled size;
- and SHA-256 digest.

Every Agent Run and resulting evidence references the manifest ID and digest. If context changes materially, the Project Lead creates a new manifest and decides whether the run must restart or its evidence is still admissible.

## 12. Conversation context

Conversation history is not copied wholesale.

The liaison may propose a bounded conversation excerpt when exact wording affects intent, authority, correction, delegation, or revocation. The excerpt retains its conversation and message reference, user-provided status, sensitivity, and purpose.

Ordinary conversational summaries remain liaison summaries. They can assist orientation but cannot override canonical facts or recorded user instructions.

## 13. Independent review isolation

Independent review needs sufficient context to apply the criteria without inheriting the implementer’s conclusions as truth.

Reviewer context normally includes:

- objective and applicable requirements;
- constraints and Decisions;
- relevant architecture;
- candidate artifact references;
- admissible evidence references;
- explicit review criteria;
- and read-only tools.

It excludes implementation scratchpads, private model reasoning, unverified liaison summaries, unrelated repair hypotheses, and write authority. Review findings return through the Project Lead and do not directly modify the candidate.

## 14. Context updates and revocation

Context Items are versioned and attributable. Superseded items remain in history but are not selected when a higher-precedence active version controls the same claim.

When a sensitive grant is revoked or expires:

- new runs cannot receive the item;
- queued runs are recompiled before dispatch;
- active runs lose future secret resolution when the execution environment supports revocation;
- resulting evidence records which manifest was actually used;
- and already disclosed information is treated as exposed rather than assumed erased.

The framework never promises that a model “forgot” information it already received.

## 15. Failures and escalation

Compilation fails closed when:

- a required kind is unavailable;
- equal-authority facts conflict;
- the role and recipe mismatch;
- item IDs duplicate;
- a secret appears as raw content;
- a grant is malformed or unauthorized;
- a required sensitive item lacks a valid exact grant;
- or context budgets cannot retain mandatory material.

The Project Lead classifies whether to recollect context, reconcile state, request disclosure, narrow the task, choose another role, or return to the user.

## 16. Liaison behavior

The liaison explains context-related interruptions in ordinary language. For example:

- “The reviewer is missing the approved requirements,” rather than “required context kind unavailable.”
- “This task needs access to the private system diagram, and that access has not been granted for this run,” rather than exposing internal grant IDs.
- “Two equally authoritative instructions conflict, so I need you to choose which applies,” rather than silently selecting the newest.

The liaison does not reveal the sensitive item while asking for permission to disclose it.

## 17. Bootstrap implementation

The initial implementation provides:

- Context Item, Context Recipe, Disclosure Grant, and Context Manifest schemas;
- implementation and independent-review recipes;
- deterministic source precedence and conflict detection;
- scope, expiry, relevance, sensitivity, and budget filtering;
- exact project-, role-, run-, and item-bound disclosure;
- secret-reference-only enforcement;
- tool and network allowlists;
- deterministic manifest digests;
- and tests covering least-context selection, precedence, conflicts, grants, expiry, secret handling, budgets, and reviewer isolation.

## 18. Acceptance criteria

V3.1-ARCH-07 is acceptable when:

1. Every Agent Run receives a versioned Context Manifest rather than ambient project history.
2. Every included item has source, integrity, sensitivity, scope, and relevance metadata.
3. Context selection is deterministic for identical inputs.
4. Higher-authority facts take precedence and equal-authority contradictions stop compilation.
5. Liaison summaries and assumptions cannot become authoritative by declaration.
6. Confidential, restricted, and secret disclosure requires an exact, unexpired grant.
7. Grants are bound to project, role, run, item, purpose, grantor, and authority.
8. Raw secret values cannot enter context storage or manifests.
9. Context and permission budgets cannot silently drop required material.
10. Independent reviewers receive read-only, isolation-preserving context.
11. Tool and network access are allowlisted in the manifest.
12. Representative recipes and deterministic tests pass.
