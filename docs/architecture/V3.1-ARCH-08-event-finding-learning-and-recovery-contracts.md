# V3.1-ARCH-08: Event, Finding, Learning, and Recovery Contracts

**Status:** Proposed architecture baseline  
**Version:** 0.1  
**Date:** 2026-09-16  
**Depends on:** V3.1-ARCH-01 through V3.1-ARCH-07

## 1. Purpose

This specification defines the durable execution history that lets V3-AIDLC recover safely after an interruption.

In plain terms, the framework must be able to answer:

- What definitely happened?
- What was merely attempted?
- Which work is still owned by a live agent?
- Did an external action possibly occur before the interruption?
- Which problems remain unresolved?
- What did the project learn?
- What can safely resume automatically?
- What requires verification or a user decision?

Conversation history is not sufficient for those answers. Recovery is reconstructed from canonical events, leases, evidence, findings, learning, and external observations.

## 2. Durable Event Envelope

Every material state change uses an append-only Event Envelope containing:

- schema and event IDs;
- project and stream IDs;
- contiguous project sequence;
- event type;
- aggregate type and ID;
- occurred and recorded times;
- accountable actor type and ID;
- idempotency key;
- optional causation and correlation IDs;
- typed payload;
- previous-event hash;
- and current-event hash.

The hash chain detects altered, removed, reordered, or inserted history. It is an integrity mechanism, not a substitute for storage access controls, backups, or cryptographic signing where those are required.

## 3. Append-only and idempotent writes

Events are never edited in place. Corrections append a new event that references what it corrects or supersedes.

Every append includes an idempotency key representing one logical action. Retrying the exact same append returns the existing event. Reusing the key with different event data fails. This prevents transport retries from recording the same action twice or changing its meaning.

Before an event enters history, the State Kernel verifies:

- required fields and timestamps;
- contiguous sequence;
- one-project boundary;
- unique event ID and idempotency key;
- previous-event hash;
- current content hash;
- and that a causation ID references an earlier event.

The readable snapshot remains derived state. Event integrity does not make the snapshot independently authoritative.

## 4. Event vocabulary

Event names use stable domain-oriented forms such as:

- `intent.recorded`
- `work-package.planned`
- `lease.acquired`
- `run.dispatched`
- `run.heartbeat`
- `run.completed`
- `evidence.collected`
- `check.evaluated`
- `gate.evaluated`
- `finding.opened`
- `finding.resolved`
- `learning.recorded`
- `decision.recorded`
- `authorization.evaluated`
- `recovery.started`
- `recovery.action-selected`
- `checkpoint.created`

Event types are versioned contracts. A payload field cannot silently change meaning under the same schema version.

## 5. Causation and correlation

`causationId` identifies the earlier event that directly caused an event. It must point backward within verified history.

`correlationId` groups events that belong to one broader request, Agent Run, repair attempt, decision exchange, or recovery session. Correlation supports tracing but does not imply causation.

The liaison’s conversation and message IDs may be correlation references, but conversational ordering cannot replace canonical event sequence.

## 6. Findings

A Finding is a durable, actionable problem or concern discovered during execution, verification, review, integration, or operation.

It records:

- stable ID;
- exact project, subject, and revision;
- source event;
- category and severity;
- status;
- summary and details;
- supporting evidence;
- accountable owner role;
- discovery time;
- and terminal resolution details when applicable.

Categories include defect, risk, evidence gap, security, compliance, ambiguity, integration, and operations.

Statuses are open, acknowledged, repairing, resolved, accepted risk, and superseded. Terminal states require a resolution, resolution event, and time. Resolved findings require resolution evidence. Accepted risk requires a recorded Decision. Superseded findings identify their replacement.

An open Finding cannot include terminal-resolution fields. A resolved Finding cannot silently reopen; new evidence creates a new Finding or an explicit governed transition where the model permits it. Accepted risk may later return to repair when authority or circumstances change.

## 7. Learning

Learning records a reusable conclusion rather than an unresolved problem.

Types include:

- validated fact;
- negative result;
- hypothesis;
- decision rule;
- recurring pattern;
- and counterexample.

Every Learning retains at least one source Finding, event, or evidence record and declares applicability tags. Confidence is tentative, supported, or validated. Validated Learning requires evidence.

Learning may be active, superseded, or retracted. Supersession and retraction retain a reason and event reference. They do not erase the earlier conclusion from history.

A Finding should not be relabeled as Learning merely to make a project appear complete. Findings require disposition; Learning changes future planning and context.

## 8. Negative learning

A well-supported negative result can be a successful outcome for an Investigation or Feasibility Route. For example, proving that an API cannot meet a latency threshold may save substantial implementation effort.

That Learning does not make the same result acceptable for a Production-Ready Route whose outcome requires a working capability. Route semantics determine whether the project answered a question or delivered a product.

## 9. Execution Leases

A lease establishes temporary, exclusive ownership of a schedulable resource.

It records:

- lease, project, resource, and Agent Run IDs;
- acquisition, heartbeat, and expiration times;
- status and attempt number;
- exact Context Manifest;
- dispatch-contract digest;
- and idempotency key.

Lease times must satisfy acquisition ≤ heartbeat ≤ expiration. Active leases prevent duplicate dispatch. Heartbeats extend ownership only through an authorized lease update event.

Lease statuses are active, released, expired, and revoked. A timestamp passing does not rewrite history; recovery observes that an active lease has passed its expiration and records the resulting action.

## 10. Recovery inputs

The Recovery Planner uses:

- a verified event chain;
- current durable leases;
- exact dispatch and Context Manifest identities;
- completed-run events;
- accepted evidence;
- retry and authorization budgets;
- known external-effect observations;
- and current time.

It does not infer completion from an agent’s last chat message, an uncommitted workspace change, or the absence of an error.

## 11. Recovery actions

| Action | Meaning |
|---|---|
| `wait_for_lease` | A legitimate lease remains active; do not duplicate the work. |
| `reclaim_and_requeue` | A local, reversible run was abandoned and safe retry budget remains. |
| `verify_external_effect` | An action may have affected the outside world; inspect reality before retry. |
| `reconcile_completed_run` | Completion or effect success exists but durable execution state is incomplete. |
| `reconcile_orphan_run` | A dispatch and its lease history do not form a safe resumable state. |
| `escalate_attempt_budget` | Safe retry limits are exhausted. |

Recovery Plans record the verified event sequence and one reason for every selected step.

## 12. External side effects

Potentially external actions include deployments, messages, purchases, payments, ticket creation, database mutation outside the transactional state boundary, and API calls with real-world consequences.

When a lease expires after such an action may have started, the planner does not retry automatically. It first queries the authoritative external system using the effect or idempotency key.

- Confirmed success leads to reconciliation without repetition.
- Confirmed absence may permit a policy-authorized retry.
- Unknown state remains blocked for verification or escalation.

This protects against duplicated releases, notifications, transactions, and other non-idempotent effects.

## 13. Recovery algorithm

On wake after interruption, the Project Lead:

1. verifies database integrity and event hashes;
2. verifies contiguous sequence and causal references;
3. rebuilds current materialized state from the last trusted checkpoint plus later events;
4. compares projected state with stored entities and repository facts;
5. identifies dispatched runs without accepted completion;
6. reconciles their current leases;
7. checks external effects before retrying consequential work;
8. evaluates attempt and authorization budgets;
9. produces a deterministic Recovery Plan;
10. records selected recovery actions before executing them;
11. recompiles context and rechecks permissions for every requeued run;
12. wakes the normal Project Lead loop.

If history integrity fails, normal execution stops. The framework does not “repair” the event chain by discarding inconvenient events.

## 14. Checkpoints and replay

A checkpoint is an optimization, not a replacement for history. It records:

- last included event sequence and hash;
- state schema version;
- materialized-state digest;
- framework and policy versions;
- repository revision where applicable;
- and creation event.

Recovery verifies the checkpoint, then replays later events. A corrupt or incompatible checkpoint can be rebuilt from earlier verified history.

Snapshots used for human readability remain marked non-authoritative.

## 15. Concurrent and out-of-order activity

Workers may finish concurrently, but canonical events receive one project sequence inside the State Kernel transaction. Event occurrence time does not determine state order.

Late results from an expired or revoked lease do not automatically update the project. The Project Lead compares their lease, run, context, subject revision, and evidence against current state. Useful evidence may be retained, while stale mutation proposals are rejected or replanned.

## 16. Resuming in a new chat session

The new liaison uses a project reference to request a Project Lead summary reconstructed from canonical state. It does not ask the prior chat to recreate current truth.

The Project Lead returns:

- current Intent and approved scope;
- active Route, Workstreams, Units, Stages, and Modes;
- active and blocked work;
- unresolved Findings and Decisions;
- applicable Learning;
- current leases and recovery actions;
- last verified checkpoint;
- and the next authorized action.

The liaison explains that summary in layman’s terms and preserves any new correction or direction through ARCH-05.

## 17. Liaison behavior

The liaison distinguishes:

- “The work completed, but its status needs to be reconciled”;
- “The work stopped and can safely be retried”;
- “The external action may already have happened, so it must be checked first”;
- and “The retry limit has been reached and needs a decision.”

It does not describe every expired lease as a failure or tell the user that work was repeated when recovery only reconciled existing results.

## 18. Bootstrap implementation

The initial implementation provides:

- Event, Finding, Learning, Lease, and Recovery Plan schemas;
- append-only hash-linked event validation;
- causal-reference and sequence verification;
- idempotent event append semantics;
- Finding validation and state transitions;
- source-bound, confidence-labeled Learning validation;
- lease validation;
- deterministic interrupted-run recovery planning;
- external-effect verification before retry;
- and tests covering tampering, duplicate delivery, orphan work, expired leases, retry budgets, completed effects, Findings, and Learning.

## 19. Acceptance criteria

V3.1-ARCH-08 is acceptable when:

1. Material execution changes are represented by append-only, attributable events.
2. Event sequence, hashes, causation, and idempotency are validated before append.
3. Duplicate delivery cannot create duplicate logical actions.
4. Findings remain separate from reusable Learning.
5. Terminal Findings require explicit, attributable disposition.
6. Validated Learning retains evidence and applicability scope.
7. Leases prevent duplicate active ownership and identify abandoned work.
8. Unexpired work is not duplicated.
9. Expired reversible work is retried only within budget.
10. Possible external effects are verified before any retry.
11. Confirmed external success is reconciled rather than repeated.
12. Recovery does not depend on the previous chat session.
13. Broken history stops normal execution instead of being silently rewritten.
14. Representative recovery scenarios pass deterministically.
